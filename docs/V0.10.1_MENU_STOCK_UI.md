# v0.10.1 · 隐藏菜信息条修复 + 菜单库存可做份数

**状态：设计已确认，待实现**  
**项目基线：main v0.10.0（实际版本以代码为准）**  
**背景：用户 v0.10.0 iPhone 竖屏截图指出备餐窗口的隐藏菜提示被挤成一条细字，与原库存检查、预制部分竞争空间；常规菜单选择看不到目前库存最多能做多少份。**

## 目标与范围
只做 UX 和可信库存计算，不创造新经济规则。不改 1 款稀有隐藏菜、每日 1–2 份、双通道贵客和正常每日市场。

1. 在 **菜单编排主页和“更换第 N 道菜”列表**展示“可做 X 份”，计算依据为实际选中工艺 `recipeCraftSnapshot(s,id).ingredientIds`，**每种重复食材算多次**。
2. 若隐藏菜已经预留了稀有原料，普通菜的可做份数必须 **先扣隐藏菜逻辑预留**。不能显示仓库物理总数误导玩家。若指定普通菜与隐藏菜为**同一菜谱**，按当前引擎规则互斥：菜单选择该菜时提醒会撤下当前隐藏菜；切换隐藏菜状态立即重新计算。
3. 对当前已安排的三道菜，显示每道菜的“可做 X 份”而不是将所有三道菜的这些数字相加当成全晚可产量：它们共用食材，提示是**单菜最大可做份数**，并说明“多道料理共享库存”。
4. 菜单库存 0 时 **允许选菜**，但显式提示“缺料 · 可做 0 份”，让玩家有空间通过探索/采购再备货；保留现有“准备开门”风险提示。
5. 隐藏菜选项显示“当前可做”以及“今晚限量”。针对用户截图修复备餐面板内的隐藏菜提示：**不可再挤成细小、无边界的浮字**；改成有对比度的单行/最多两行浅边框**内联营业计划摘要**，与库存检查形成独立但紧凑的自然内容流。作为 flex 子项不可被压扁（`flex-shrink:0`）；必要时现有准备卡自身滚动，不遮住屏幕底部“开门迎客”栏。
6. UI 不引入新的主页卡片、不增加手指操作层级、不强行展示奇幻区域称呼。小宽度 320px、短屏高度 650px 用实际文字长度约束，字号不低于可读范围；浅底用深字、深底用浅字。

## 代码与验收
- 计算集中在 `src/engine.js` 的纯函数，供菜单页、候选列表和已有稀有菜单选择器共同读取，不复制不同公式。
- 预留源 `premiumReserved` 只影响普通库存可用额，不应修改实际仓库，不取消现有真实订单按唯一流水扣料规则。
- 测试单料、多料、重复料、当前工艺变更、零库存、隐藏菜占用、库存购买后复算、不修改输入 state。
- 前端 UI 断言菜单本页及候选列表都包含可做份数、隐藏菜文本和样式安全；CI `npm test` + Vite build + standalone 构建，用户再用 iPhone 真机检查视觉。
- **不包含客人图鉴**；交给 v0.10.2。
