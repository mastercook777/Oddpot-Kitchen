# v0.15-D · 云港真实订单、好感度与双章供给审计（2026-10-25）

**状态：执行中（先行方法规格；仅审计，不擅自修改满意度、员工、探索、工资或存档）**  
**代码基线：main v0.15.0-alpha.9 / PR #92；目标：弄清低满意与顾客大量超时离店究竟由口味、缺料、炉台产能、送餐还是耐心造成，并量化旧世界委托的真实边界。**

## 1. 可核查的已知机制
- Cloud 原生居民 cloud_docker 的基础耐心 23 秒，cloud_weaver 31 秒；入座时将门外真实排队时间折为耐心削减，最低 8 秒。跑堂在顾客入座后增加真实耐心（原逻辑）；顾客在烹饪、取盘、跑堂手上超时均被标记 `left` 并扣区域声望。
- 只有真实送达、用餐评价后才能结算销售；实际满意度为口味匹配 50% + 料理品质 30% + 服务速度 20%（以及已消费的事件 Buff）。**差评（sat<50）、超时弃单及未达标的日任务必须分开**；某一道菜占比较大不自动等于差评。
- 厨房为真实物理工位。云港初始两厨位：本地帮厨优先 WOK，主厨位置决定另一厨位产出；`reassignIdleCooks` 当前只在三厨位排班时启用。不能把 `walkable:false` 自动烹饪的乐观结果当手机现场。
- 熟菜 v0.15-I.1 只在真正出锅未送达时进入当晚 `prep`，相同 recipe/variant 复用，收入仍来自真实 `sale` 交易，不跨日；需量化真正减少几份损耗。
- Cloud 初始世界有鸡肉、洋葱、云谷米、浮苔叶、雷羽蛋；后续每天本地市场真实上架四种普通食材；出口券须原店**真实卖菜**才获得，云港每天最多一箱八份原世界材料。这条逻辑不会被静态脚本视作无限免费供应。

## 2. 量化实验与对照组
A. **隔离服务能力**：同一 24–48 个固定 seed、同云港菜单 `sour_rice / cloud_rice_chicken / moss_soup`、相同初始足量普通库存和相同工资/设备：
- `auto` = `walkable:false` 自动出餐，作为纯算法上限，非玩家手机操作；
- `right` = `walkable:true` 主厨固定右厨位（左帮厨 WOK），并不主动端菜，代表了解两个角色分工的最低操作；
- `left` = `walkable:true` 主厨固定左厨位（与当地帮厨站同一厨位），测出另一厨位无人操作的最差情况；
- `pass` = 主厨在传菜区，模拟忙于取盘或完全没有照看炉位的状态；
- `waiter` = 在右厨位且已真实雇用小羽（成本单列），区别「无人传菜自送」；
- `two_waiters` = 满当地首星并付费聘用小澜，小羽与小澜两条真实送菜任务；属于成熟经营对照，不假定新店免费拥有第二跑堂。
固定模拟时长最多 150 秒，原事件选择 `steady` 或零成本选择，不使用人为强制完成服务。每个 `seed` 配对比较真实到店、实点、实售、入座后超时（按queued/cooking/pickup/delivering分段）、排队放弃、缺料拒绝、顾客口味 `fit`、品质、速度得分、服务耗时、成本、声望增量、成品回收/再用/过期；第二栏位不营业时允许真实惨败，绝不自动补厨师。

B. **多日供需**：至少 12 seeds × 18 个云港营业日：
- `market_only`：初始足量库存仅供开局，后续只通过真实 `ensureDailyMarket` 与 `purchase` 补供，不注入外生探索掉落；记录市场购入量/花费、缺料、库存与现金。不是「云港正常探索」的替身；
- `conditional_freight`：只对进入云港前确实从旧餐厅真实营业赚取的券试验一次 8 份进口箱；不得脚本平空设定 `ferryCredits=1`。如果脚本没完成旧店真实营业就不能推断出口收益。
为隔离供给，在独立单夜实验可以给定100份初始库存，必须明确称为**外生诊断样本**；不能拿它得出的利润或可连续营业时长当作自然资源结果。
菜单与员工/厨具升级属于事先固定政策，而非预知未来客人，已有本地菜谱是否开放需区分「老店已研发云港进度」与「新入港」；不得把人为设置已研发称作合法自然解锁。记完整入口状态/工资与设备投入。

## 3. 决策门槛（非先验结论）
- 若相同顾客/菜单/库存下 `left` 和 `right` 的完成率差异显著、无厨师 POT 有长期任务积压，优先修 2 厨位岗位提示或真实帮厨跨位支援；新增劳动位移必须消耗真实秒数，不能隐形多出第二个帮厨。
- 若确有足量厨房出品而 `pickup/delivering` 超时居多，先校正送餐和超时路径（保留实际落桌才收钱），评估跑堂存在的真实增益，再考虑降低取菜工作量。
- 若等待问题在人员/设备都覆盖的条件仍明显，才考虑小幅调整 cloud_docker 等具体客群耐心；必须用相同 seed 的对照结果记录真正提升成交、不削弱星章难度，不统一给所有顾客加秒。
- 若 `fit` 低或本地菜单缺乏覆盖，下一步先补云港食材/菜谱/客群对应而非用加耐心掩盖；v0.15-K 镜露花园仍是独立内容提案。
- 任何改变须有相同 seed 严格成对模拟、对应单元回归、版本化规则、真实存档与经济边界。审计结论若没有数据支持则写“待验证”，不预设必要改动。
