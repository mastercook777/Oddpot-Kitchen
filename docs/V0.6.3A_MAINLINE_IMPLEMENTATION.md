## 1. 这一版真正改变了什么

正式游戏的「料理实验」阶段已接入连续实时研发：

1. 选择**炒锅 / 深锅**，然后只选 2–3 种食材，不预先编排顺序。
2. 开火后用食材按钮自由投料；第一份入锅后启动真实时间累积，最长 19 秒，全部下锅后可自行起锅。
3. 炒锅：**翻炒、颠勺**；深锅：**轻搅、收汁**。每种动作每锅最多一次。可点击按钮，也支持锅面相应手势。无三拍回合或精准 QTE。
4. 锅内食材通过常驻 DOM 图标显示并实时移动；独立 CSS 绘制锅体，减少上一版 Canvas/emoji 不可见或重影的风险。
5. 系统记录每份食材入锅时机、动作时机、动作时锅内食材、起锅时间；按当前熟度判定夹生、略欠火、成功或焦糊。
6. **每次完成研发（成功或失败）都在统一引擎通过一次性事务真实扣料**；漏下料、明显夹生、严重焦糊不解锁菜谱，略欠火可收录为较低品质菜。
7. 成功后保存 `CookVariant`，同一道菜按不同工艺、食材签名和辅助事实保留独立版本。图鉴可直接点击设置默认版本，并展示该版本的品质、招牌适配程度等。
8. 现有 12 道正式菜 ID 和旧存档的最高品质仍兼容；首次加载旧存档会为已掌握菜谱创建 `legacy-标准工艺` 版本。不丢原来三道菜单、员工、金币或库存。

**重要：本轮的“设为默认工艺”是研发表与图鉴状态的准备工作，暂未改变顾客点单、营业耗时、菜价、员工餐或探索效果。** v0.6.3-B/C 与 v0.6.4 才会连接后续经营。

## 2. 菜谱与适配数据

- 原本 8 食材：任选 2–3 共 84 种食材组合，再乘炒锅/深锅为 **168 种有效签名**；原有「辣椒炒肉」鸡肉或牛肉都共用同一个 recipeId，所以唯一菜谱 ID 共 **167 个**。
- 其中 **12 道原主线 + 6 道新增精选菜**的适配配置来自 `docs/data/v063a_recipe_technique_profiles_v01.json`，已复制进 `src/recipe_profiles_v063.js`。
- 其余组合使用带固定 ID、可售基础时间/价格/味型和稳定名称的轻量模板兜底，不会因为缺少手工文案而被判“未知料理”；特殊招牌收益暂不向生成菜自动扩散。
- 工艺识别和菜谱适配分开：动作事件推导 `home / home_even / aroma / burst / pot_home / gentle / reduced`，再按 recipeId 查专属适配。**不会因为爆炒这个词条而让任何炒菜自动减少 1 秒**。
- 目前配对的 `guestFitDelta/timeDeltaSeconds/priceDeltaCoins` 保留为设计**元数据**，不得在 v0.6.3-A 阶段当成正式经营效果。

## 4. 重要兼容约束

- `SAVE_KEY` 保持 `oddpot-prototype-v04`，`version:4` 保持不变；新字段为 `recipeVariants` 与 `activeVariantIds`，以非破坏方式新增。
- 旧 `s.recipes[recipeId]` 仍然是**品质数值**。为了保护现有运营，研发成功仍将其更新为历史最优，现有餐馆/员工餐的输入结构未被改变。
- 为菜谱新增一种工艺**不是得到一份免费餐点**。研发失败也通过事务扣料；日常营业仍按原来的 `consume` 和落桌记一次收入机制运行。
- 研发使用替代食材（例如牛肉辣椒炒肉）时版本数据保存 `ingredientIds`；但直到 v0.6.3-B 完成订单版本快照与材料签名对接，自动营业仍使用旧菜谱的默认原料表。这一点在 B 阶段必须优先处理。
- 单日餐饮结算、双工位、桌位、真实顾客评价、员工上限与三日厨王逻辑本轮未改。

## 5. 自动验收已覆盖

- 8 种食材组成的 **168 种锅具×组合** 都能匹配菜名，保留 12 道旧菜 ID。
- 同一牛肉+洋葱在炒锅能得到家常、爆炒、香味十足，换成深锅是另一菜谱身份。
- 蒜+菌菇、菌菇+鸡肉在合理时序翻炒时可识别香味型工艺（修复旧实验的肉类偏置）。
- 辣椒炒肉的爆炒与焦香蒜牛的爆炒在配对元数据上可以有不同工时变化；清炒双蔬不会继承统一爆炒收益。
- 早起锅失败不可收录，但消耗真实食材；再次研究可成功且不会生成伪造的 legacy 版本。
- 已解锁旧菜创建标准工艺；用户可以选择版本而不改变原最高品质、金币、菜单或员工业绩。
- 19 秒自动起锅最多消耗一笔原料事务，不会重复结算。
- `npm run build` 实际构建成功；`standalone.html` 内联脚本通过语法解析。
