# v0.10 设计草案｜招牌菜 × 熟客 × 口碑传播 × 主动揽客

**状态：方向已获玩家认可；本详细方案为待审草案、尚未写入正式游戏代码。**  
**规划时间**：2026-10-13  
**实装基线**：v0.9.5，修改前必须复查仓库 main；[当前状态](PROJECT_STATE.md) / [路线图](ROADMAP.md)  
**目标**：让玩家做出的一道好料理，成为餐厅能持续吸引真实顾客与增加实际营业额的长期资产；游戏经营不应只靠增加后期难度。

## 1. 为什么要做

v0.9.5 已有研发、三道菜单、真实顾客评价、随机采购、两/三张桌子、双炉台、员工、声望与累计收入，但这些系统之间缺少关键的**口碑回流链条**：

> 研发出高品质料理 → 选为招牌并招揽某类客人 → 顾客真实到店、上桌、用餐、给出评价 → 累积客人关系与菜名声 → 第二天有人为了这道菜再来，甚至带来朋友 → 真实需求与收入增加 → 玩家投资厨位、员工、座位、补货。

系统的主要挑战来自**玩家做生意做大后造成的真实产能瓶颈**，而不是运营轮次机械加血、加订单或强行降分。

### 玩家连续三天的目标体验（示意，不是已实现）

- 第一天：研究好品质的「火椒噼啪肉」，在已上架三菜中指定为今日招牌，铁甲矮人更容易关注该料理；实际评价很好后某位食客记录它。
- 第二天：玩家在客人名单里再次看见同一位矮人，知道对方喜欢这道菜。客人**确实进入真实订单流并占座/消费**，才获得该次销量和满意度。
- 第三天：该熟客可能带一位同伴到店，坐不下就真正等位，缺料就真实失单。玩家决定扩容/换工位/补货/调整菜单，而不是领取自动加成。

## 2. v0.10 最小可玩范围

### A. 招牌菜（玩家主动选择）

- 玩家在**现有三道上架菜**中选择 1 道为“今日主推/招牌”（建议初版最多 1 道；尚未作为最终数值确认）。不新增第四道菜单，也不新建后台独立菜品生产规则。
- 默认未选择时，现有顾客逻辑与经济保持一致；选中后，作为真实客群倾向、宣传和后续口碑关系的入口。
- 菜品品质来自现有 `recipeCraftSnapshot(s,recipeId)` 及有效工艺，不使用另一套脱离研发的“招牌等级”。允许以后换招牌，但保存过往关系。
- **不是直接全菜售价 +X%**：价值主要体现在顾客需求、回访和可追踪的餐厅成长。

### B. 具名熟客（真实顾客长期身份）

- 由已有 `CUSTOMERS` 四类客群派生少量**具名身份**，使用原程序像素外形；在既有 order 上附加 `regularId` 或 `guestId`，避免创造不占座的“背景熟客”。
- 正式关系只在实际完成用餐与评分后增加；撤回/重读同一次消费不得重复增加关系。老存档初次升级时为空，不影响现有顾客。
- 每位熟客记录简洁信息：稳定 id、对应客群、喜欢的 `recipeId`、到店次数、最近来店日、最近评价 / 关系级别。**数据不应包含假想已访问次数**。
- 熟客不是每天必来：由可重现的游戏日种子、关系级别和餐馆当前菜单决定真实回访机会；已在出单流里出现则通过 existing `orderId` 正常等待、点菜、被招待、评价和离开。
- 熟客身份以 NPC 的短句或轻量符号提示，不要把整套人物档案堆在营业 HUD 上。可在现有营业日报或菜单二级页面按需查看。

### C. 口碑传播（必须有真实新增需求）

- 每次成功接待熟客，按照**真实满意度阈值**记录一次口碑事件。回访和朋友转介绍只能在下一次 `serviceDayPlan` 制作真实顾客计划时产生；不能在已生成的夜间订单上后插幽灵订单。
- 同一天多个好评不能无限生成新客。初版建议明确上限（例如**每营业日最多 1–2 位**由口碑带来的新增潜在到店，**待调优确认**），并在日报里解释新增来源。
- 新客仍受餐桌、等待、厨房产能、库存和订单失败机制制约；**增加潜在客流不等于自动增加利润**。
- 声望从累计数值变为影响顾客选择的经营资产，但不得让声望直接生成没有真实来客/就餐的销售额。

### D. 轻度主动揽客（建议最小化）

- 玩家可选择「不宣传」或「推广今日招牌」的一个简单操作。选择推广需支付**一次真实金币成本**，并引导特定口味客群到店；可不做全套营销商店。
- 推广成功的定义不是点击按钮，而是在次日实际有符合目标的订单/销量和口碑变化。玩家同样可以不宣传、依靠已有声望。
- 推广成本、出现概率等目前仅为**建议测试变量，不是现行数值**。若系统复杂度或 UI 干扰过高，可将付费推广单独顺延，v0.10 先完成招牌+熟客+自然回访闭环。

## 3. 与当前代码的具体衔接（实施前要核对最新源码）

| 现有入口 | 可复用点 | 必须注意 |
|---|---|---|
| `src/data.js` 中 `CUSTOMERS` / `RECIPES` | 四类现有奇幻顾客口味、菜谱标签、价格 | 延伸身份而非替换客群；不要回退到旧普通人类客人台词 |
| `src/app.js` 的 `menu()`、`prep()` | 三菜上架与开业前准备 | 优先在原菜单卡做一颗可见但不拥挤的招牌标记；别引入多重浮窗 |
| `src/engine.js` 的 `recipeCraftSnapshot` | 已有工艺、真实 ingredients、品质等 | 招牌口碑要尊重当前工艺，已接单保留原快照 |
| `serviceDayPlan` / `createService` / `selectArrivalDish` | 到店客流和点单源头 | 所有回访/转介绍必须在真实到店计划与订单流内，具名客有稳定 ID |
| `closeService`、订单评分/真实销售事务 | 餐馆关系的结算时刻 | 按订单唯一 ID 保证读档后不重复增长，失败订单不能计满好感 |
| `s.history`、`s.reputation` | 长期经营与报表 | 可在日报增加简短“熟客回访 / 推荐到店”数量；不新增虚假收入 |
| `save/load`、`version=4` | 持久关系与进度 | 新字段默认空结构，迁移兼容长期旧档，禁止清档 |
| `src/diner_ambience_v077.js`、`src/pixels_v041.js` | 已有身份化像素 NPC | 尽量只加一句可理解的熟客对白，不要求正式美术资产 |

### 建议的数据模型（示例，未确认字段最终命名）

```js
s.restaurantGrowth = {
  signatureRecipeId: null,         // 必须在三菜菜单中才能被指定
  regulars: {                      // key 是稳定、去重的 guestId
    // "dwarf_miner_01": {segment:"adventurer",favoriteRecipeId:"chili_meat",visits:2,affinity:2,lastVisitDay:8}
  },
  promotion: {dayKey:null,recipeId:null,cost:0},
  referrals: [],                  // 下一日候选；真正入场才算实际到店
  settledRelationshipOrders: []  // 幂等集合，限制持续存档体积
}
```

**实现注意**：不得在纯 UI `render()`、随机对白选择或 `load()` 时创建口碑利益。最好把关系结算绑定现有 `sale-orderId`/真实订单完成机制，避免自动送餐与玩家送餐各记一次；不应重置旧档的已赚金币/声望。

## 4. UI 设计硬约束

- **菜单页**：一眼看懂三道菜谁是招牌。可使用选中状态/小标记，不额外重复显示菜价、厨位或成长教程。
- **营业准备**：当前已有锅具、员工餐、预计客流、v0.9.5 库存风险、预制菜；**不能再塞第二张营销面板**。如需推广，优先在菜单页操作。
- **营业现场**：最多让具名熟客触发简短一次性对白或低调标识；维持现有气泡上限、真实客人落椅和界面避让规则。
- **日报**：仅增加可证实的熟客回访/好友推荐/口碑变化摘要，点击二级详情再查看关系，不做满屏人物卡。
- 世界观通过奇异 NPC 行为与对话表达，不出现“咕噜门廊/菌灯角落”一类无功能的标签。继续保留复古程序像素风。
- 320px 宽、短屏、iPhone Safari safe-area、可达主按钮与摇杆是强制验收；色彩对比度要避免 v0.9.3 采购页浅底浅字再次发生。

## 5. 需要具体验证的经营结果

- **同条件对照**：同一种子、相近食材与厨位配置，经营数日后选择招牌的组 vs 未做宣传的组，实际出现回访、真实需求、营业额差异；没有必然赚钱保证。
- **无客作弊**：因等待超时、食材不足、经营失败离开的熟客不会凭空生成满意/已服务/已卖出记录。
- **产能生意关系**：队伍人数增多必须体现在真实座位占用/候席窗口，不是自动累加金币。
- **长期存档**：玩家第 20 天、6 座、已有大量食材/声望的老档能进入该系统，不丢失已实现升级、菜谱/工艺、财务历史。
- **阶段性证明**：玩家看到「这位客人上次来过」「这次带朋友来了」并可通过实际订单查询证据，才算有经营成就感。

## 6. 最小版本与排除项

**建议先做**：1 个招牌槽 → 至少两种具名熟客模板 → 实际回访和一次真实传播 → 轻量日报记录 → 旧存档迁移与测试。  
**可后补**：更多具名客模板、经营成就相册、付费推广完整系统。  
**不在此版**：VIP 预约/隐藏菜单（v0.11 候选）、商人新食材与专供（v0.12 候选）、第三个真实厨位或新大店面（v0.13 候选）、正式美术资源。

## 7. 待确认，不能自认已经拍板

1. **招牌槽数量**：先 1 个是我的减法建议，不是用户指定；是否要长期扩到 2 个？
2. **熟客身份密度**：初期几个具体可记住的 NPC？是固定名字还是每个阵营一组随机姓名？
3. **关系门槛与回访强度**：要能感受到正反馈，但不能第 20 天突然每天满队，具体几日/概率/上限需实测调优。
4. **推广是 v0.10 首发必需还是第二迭代**：若纳入，需要金额、效果、失败风险与说明；不能仅凭点击生成好评。
5. **报表位置**：哪几个字段最重要，避免再造成主页面状态重复。
6. **已出现的高声望老存档迁移**：应让旧玩家开始建立熟客关系，而不是自动赠送没有出现过的历史熟客。

**开发决策门槛**：用户已确认“招牌菜、熟客和口碑推动真实经营成长”的方向。具体数量、转化曲线和是否同版加入付费宣传，可在开始实现前按此文档确认或记录为“实验参数”；**先更新 GitHub 设计稿，再动业务代码**。

## 7.5 本次最小闭环实施决策（2026-10-13；开发用实验参数，待验收）

**状态：开发中（仅此小节范围）。** 方向与必要闭环沿用上述用户已认可的增长目标；以下数值均为可调原型假设，不代表玩家已确认平衡结果。

1. 当晚最多指定 **1 道**菜单内料理为招牌；无选择时完全保持原有算法。换掉该菜会清除当前主推，但保留已积累的熟客关系。不上第四菜，不涨售价。
2. 先用现有矮人/菌帽两类像素客形派生两位稳定具名客人。仅在菜单和客群匹配的真实订单池中标识初见/回访身份。口味匹配条件仍执行原有点单、餐桌/耐心和缺料规则；有已知喜好的熟客在可点菜条件下优先选择其喜欢菜。
3. 只有已上桌消费并产生真实评价且满意度 ≥ **80** 的具名客订单，才增长其到店关系，并登记最多 **每天 1 条**下次营业可兑现的推荐线索；推荐线索只在将来的 serviceDayPlan 中转化为 **1 个额外的真实计划客人**。若无法入店或未完成订单，不计算成交；线索使用一次，不会读档复制。尝试回访使用游戏日种子确定性选择，初期实验概率 **75%**；每晚最多 **1 位具名客**，该客当晚只有一个身份。
4. 使用现有 orderId / sale-流水账，关系结算也用 `relationship-orderId` 唯一事件防重复；推荐订单进入同一 `orders`，保持同一取餐、落桌、售价、库存与碰撞路径。评委挑战最后一个指定订单不允许被推荐单覆盖。
5. 老 `version:4` 存档仅补空 `restaurantGrowth`；不虚构历史访问、不触碰金币/菜谱/房屋。查看菜单/预计客流必须是纯读，无奖励副作用；日报单列实际**已到店**的熟客回访和推荐来源，同时区分真正已送达数。
6. UI 只在原菜单列表的每道菜旁加轻量招牌操作、在既有营业场景放极短识别标签、日报增加一条经营口碑摘要。无需新营销面板；本阶段**不做付费推广**。
7. 自动验收：无招牌回归、同 seed 重放、首见→评价→次日回访、推荐真实加单/满座等待/缺料失败、状态读档、旧档迁移、订单只算一次、第三天评委订单保持、320px 样式与离线构建。手机 Safari 真机仍单列待验收。

**明确排除**：VIP/特殊预约、随机姓名池、第三炉台、完整宣传花费、正式美术；不因原草案中未决的数字假设扩大本次范围。
