## 0. 设计决策与版本边界

原路线图一度称「v0.13-B 二星」，但 v0.13-B 已用于共享锅具与动态补位（v0.13.0-alpha.2）。为避免冲突，本功能统一称 **v0.13-C 第二星章**。第三厨位/第二帮厨已经可用，不应被二星“再次解锁”；烤架/烤叉、第三星、异界传送门分别独立排期，不进入本次开发。

核心玩家问题从「有没有足够的金币」转为「我能否针对两种经营考题，合理搭配菜谱、库存、设备和团队，在真实高峰把顾客照顾好」。玩家主动报名、看到公开门槛、用正常真实营业完成考题，在日报收到能解释失败原因的反馈。不能生成虚构订单或第二套营业模拟。

## 1. 双夜流程

**资格建议（开发前量化验证）**：已获得首枚万味星章，已拥有第四桌，累计营业日数达到第七天或同等自然进度；不硬性要求已经购买第三厨位、雇佣小炭、厨师 Lv3 或获得稀有食材。若三个条件中任一个造成不必要的刷天数，应优先放宽。

在开门前的备餐区有一张简短可选评鉴卡，玩家主动报名。报名只在 `forecast/prep` 且当日尚未启动营业时可撤回；营业创建时冻结当晚的 stage ID 与规则。不收报名费。前两日其他玩法（探索、研发、采购、宣传）照常进行。

- **第 1 夜：「繁忙之夜」**，考量真实客人实际入座/上菜、门外排队后的流失、真实经营利润。不限菜单，无强制大排队目标；没有排队不扣“没制造队伍”的分。开店前可预览主题与缺料风险。
- **第 2 夜：「拿手之夜」**，考量顾客实际满意、交付料理的工艺、不同菜谱的真实成交与厨房协作。员工参与是额外可见的加分依据，不要求强行雇人或制造订单；菜单至少提供两种可行策略。
- 第一夜未通过：只需在下一个可用营业日重试第一夜，不扣一星，不回滚当天金币、存货、XP、销量。第一夜通过后写入下一阶段资格；第二夜未通过只重试第二夜，不重打第一夜。阶段之间允许自由经营准备、探索/研发。
- 第二夜成功：唯一事务授第二枚星章，开出一项**当下真的可使用**的经营选择，展示下一枚星的方向，但不出现不可点击的假传送门。

## 2. 真实指标与打分契约

评分必须通过已完成同一场 `service` 的冻结 `orders/events/queue/finance/recipeCraftSnapshot` 归并，不能凭空给完成单。两晚各自评分，均限制0–100并有清晰门槛和一条来自实际事件的建议。

**第一夜候选维度（数值待模拟调优）**：实际订单交付率 45%、队列体验 25%、经营利润与成本控制 30%。队列体验基于 `queue.abandoned`、`queue.waited`、`queue.maxWaitSeconds`；没有等位客按非惩罚方式处理，**绝不为了高分要求主动制造排队**。利润以含工资/宣传/食材耗用的 `report.profit` 计算，必须对未宣传、低库存、不同菜单规模公平；不可单用绝对金币奖励高价稀有菜单。可考虑与该夜可见客流规模关联的每单贡献利润或正利润达标区间，参数锁定前用真实种子验证。

**第二夜候选维度**：实际完成客人的满意 40%、已交付料理工艺/品质 25%、不同菜谱的真实销售覆盖 20%、实际员工完成工作的协同表现 15%。不雇员工时最后一轴应能通过主厨实际救场等同一订单证据获得可及分数，不能强迫付费升级。新增指标从当天已完成订单读取，不包括仅挂菜单、预制却未售的菜。品质/满意继续走唯一现有规则。

**当前不得锁死门槛**：首星原 72 与 2/3 接待率不能机械复制；本游戏四桌星章后自然约 15.6 位到店而有效上菜约 10 位，三厨位/小炭在备料充足时可改善，但低库存会有真实亏损。因此先基于至少80、最好250个相同种子的两夜数据，对两工位/三工位、员工出勤、混合/同类菜单、常规/低库存和正常宣传做控制变量回归，决定能被两种策略合理达成、但不会随便白送的阈值。若盈利项被市场采购成本扭曲，优先调整归一化方式而非增加额外金币。

## 3. 第二星奖励：必须真实落地

**当前实现候选：新增「星章品鉴预告」揽客方案（需与二星同版完整实装）**。在原 `CAMPAIGNS` 中增加一项星级要求2的付费、可选定向客群宣传，真实在 `serviceDayPlan` 增加少量有口味偏好的可追踪来客，经过门外排队、座位、实际制作与送餐、评价、销售和开门时唯一宣传扣费。比现有首星「品鉴邀请」强调菜单搭配而非单个评论家；能带来机会也可能造成排队与利润风险。**费用、额外人数、具体客群要经80种子真实经营测试再定**，不可承诺稳赚。若模拟证明该奖励与现有公会/品鉴方案策略同质，应改为真实可用的其他经营工具后再开发二星，禁止只解锁一段文案。

奖励另包括章节UI第二枚星章和后续第三星目标提示，但**这两项不能代替真实可操作奖励**。烤架与武器需先有独立可玩切片，不依赖本版的空按钮。

## 4. 数据 / 幂等 / 存档

在旧 `chapterProgress` 上增加**可选** `secondAppraisal` 子状态（例如 `{stage:1|2,requestedDay,lastAttemptDay,stage1Result,lastScore}`），沿用 schema4 和原本 `SAVE_KEY`，老档按一星状态懒初始化，不倒灌二星。现有 `ensureChapterProgress` 只允许1星，因此必须同步把上限扩至2、并防止首星在已有二星存档中再次申请。

营业创建时写一次 `service.secondStarStage` 冻结规则/阶段，日结只处理这一次真实订单；单日只能生成一份 `secondAppraisalResult`，重复 `closeService`、刷新恢复、重复点击或低信誉网络访问不再多发星/金币/工资/XP。二星奖励的 ledger key 固定（建议 `chapter-hearth-star-2`），第一夜完成与第二夜成绩采用唯一 dayKey 记录但不修改历史财务。旧已开始的普通或首星营业不被重置为二星。跨三日轮次只更新自然日期，不意外清空第二夜的待复试资格。

收入/库存/XP 使用当前 `engine.js` 唯一真实账本，评分只读；老二炉进行中营业、动态厨师补位与第三厨位并行不受影响。

## 5. 移动 UI 位置与反馈

- `prep` 现有首星评鉴区域原位升级成紧凑的「第二星 · 第1/2夜」卡，不新加常驻 HUD 和浮动按钮；320×568 禁止压住厨房/库存/开门。
- 开门前只展示**当前一夜**主题、约2–3个看得懂的判定维度与能否申请。第1夜通过后次日改写为第2夜；当日不允许免费回滚重跑。
- `report` 中独立一张易读分项卡：真实上菜数、等位流失、实际利润/满意/菜品覆盖、阶段成绩、明确“通过/未通过/下次只重试这一夜”。不与首星/厨王竞争标题，玩家总能找到普通日报和账本。
- 获得第二星后，备餐的揽客计划显示真正新开放的营销选项；不提前出现不可能点击的异界、烤架、水吧。
- 新增或改动的可见文案全部保持手机中文短句；不强制展示内部 `stageId`、地区代号或代码参数。

## 6. 建议实施任务与 Definition of Done

1. **规格与经济预演**：先完成本稿的参数审计工具/固定种子模拟，提交两夜不同菜单与人员策略的实际得分分布、极端低库存与未参加宣传样本；锁定阶段门槛和可触发的奖励内容。
2. **纯规则与存档**：独立 `restaurant_second_star_v013c.js`，负责两夜评分、状态迁移及资格判断；只有 `engine.js` 持有状态与幂等唯一提交。
3. **真实营业接入**：冻结阶段至service snapshot，日结评分/进度/财务只一次，失败正确保留当天收益；二星营销资格可运营。
4. **UI 与恢复**：报名/撤销、两个分阶段评分与结果页、下一夜延期/重试、二星奖励所对应的真实可点行为。
5. **完整回归**：v0.12-A首星、v0.13-B员工动态与共享锅具、老schema4、二炉/三炉、跳天/跨轮、最低库存、同seed确定性、320/375/390 Chrome、离线 `standalone.html`、Vite 构建及GitHub Actions。通过CI后部署 Pages 做实际 iPhone 试玩，用户主观验收**单独记录**。

**不在本次**：三颗星全部完成、其他章节传送门、烤架/烤叉与水吧；也不借二星项目重新平衡已获玩家认可的探索掉落和攻击手感。
