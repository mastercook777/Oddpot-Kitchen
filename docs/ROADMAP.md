## 三、v0.15-C 六项返工的具体验收门槛

1. **地形与动作**：餐厅能看出独立悬空结构；野外断桥/云海不是背景贴纸，危险崖缘不可穿越；风道有可预判影响，风蛾和首领不再复用第一世界攻击模板。
2. **当地雇员**：原店已雇员工不自动在云港上岗；阿岚/小羽/小栖依本地雇佣与班次进入，当地 XP 不在往返时复制；老云港档需迁移。
3. **厨位真实约束**：两个物理厨位只能覆盖两种当晚厨具；蒸笼必须占用深锅位，三种不同厨具的菜单不得成功开业；已进行中的工位快照不遭追改。
4. **跨章食谱**：旧菜可在共享图鉴阅读，但不能以隐藏菜、普通菜单、临时换菜或员工餐绕过章内食材与设备门槛；本地菜必须确实研发与消耗本地库存。
5. **图鉴可读性**：炒锅/炖锅/蒸笼/烤架分类及章内上架资格一眼清楚，不把“曾发现”误示为“本店可卖”。
6. **回旧世界有价值**：原店至少真实成交一单且营业结算，才有一张航运委托；切换、重复日报、无成交不发证；云港每当地营业日最多兑换一次普通本地补给；本地独立探索/采购仍能完成首星。

P0 的自动化边界是 320/375/390px Chrome、离线单文件、存档版本迁移、单次 ledger、两章来回切换及新/旧存档；玩家主观视觉/中文字体/手机性能和新章节经营耐玩度单独记录。**以上是验收标准，并非新一轮六项全部由玩家确认通过。**

## 四、跨系统开发红线

**迭代文档交付是阻断门槛，不是建议。** 详见根目录 [AGENTS.md 全迭代文档交付规则](../AGENTS.md)。每轮功能/修复完成要在 `docs/` 留下版本化实现与测试记录（小修可精简），并逐一复核三份主文档：正式代码变化同步 `PROJECT_STATE.md`，任务/优先级变化同步本 `ROADMAP.md`，基线/接续任务变化同步 `START_HERE.md`。经确认不变的主文档在交付记录中写明“已复核，无需更新”。设计规格先行、实际验收回写、GitHub PR 链接、下一任务入口齐备后才称完整交付；CI、Pages 与玩家真机验收必须分开。


- 餐馆是情感中心；料理研发和真实菜单 Build 是策略核心；探索服务食材与特殊料理，不变成单纯 DPS 堆积。
- 维持真实菜单、物理厨位和工作站覆盖、订单选择、供应材料、制作耗时及唯一财务账本。不得以新章特效伪造攻击/掉落，不得靠剧情对话凭空发钱/食材/星章。
- 跨章：老店资产、菜单、原料、员工不随切换复制；菜谱图鉴共享但**可上架权限按章**；云港委托必须通过真实营业产生。旧规格的“同行员工”“旧菜自然可用”已经撤销。
- 新内容先写可审查的 `docs/` 版本化规格再改游戏代码；PR 引用规格，结果写回 [PROJECT_STATE](PROJECT_STATE.md) 与本路线图，记录实际测试结果、失效边界、未完成与真机验收差异。
- 新关卡不能只换外皮；至少有**一种可感知的空间/风险规则、一种真正不同的料理或厨具决策、一种真实客群/经营压力**。未获证据前不要扩第 2 世界。
- 版本号以仓库实际 `package.json` 为准；不要把设计稿的“草案”提升成已交付、已上线或玩家已验收。
