# v0.15-D · 云港经营压力实证结果（alpha.9 基线，2026-10-25）

**性质：可复现代码内控制实验，不是手机玩家操作记录，也不是实际野外探索掉落。**  
**证据：** [审计规格](V0.15D_CLOUD_OPERATIONS_AUDIT_SPEC.md)、`scripts/audit-cloud-v015d.mjs`、`tests/v015d_cloud_operations_audit.test.js`；GitHub PR #93 / 核心测试 SHA `b0baaadb` 的 `CLOUD_V015D_AUDIT_JSON` 机器输出。

## 1 实际运行
- 12 种固定种子，间隔 2267；6 个服务组（每组12个独立营业晚）共 72 晚。相同菜单 `sour_rice`（WOK）/`cloud_rice_chicken`、`moss_soup`（POT）；已解锁品质84，相关普通材料开局外生补足到100。单独对比自动出餐、主厨固定右厨位、主厨固定左厨位、主厨停留传菜区、右厨位+小羽、右厨位+小羽+小澜。真实 100 秒营业、餐桌容量、到店、工位任务、工资、出售/废盘账本，事件固定选择零成本。`walkable:false` 只作理论对照。
- 6个种子×18个云港营业日×2方案，**216晚真实营业运算**：当地每天市场实际轮换与真实采购；玩家不外出探索，不假装跑过野外战斗。开始时人为设置云港已研发的三道菜、云港起始金币300（不是自然开局）；一次货箱方案先从主线进入云港，再回原店用外生足量仓库**真实卖菜赚到唯一一张**供货券后跨回云港，仅第一晚兑换一次 forest 8份（共六箱/48份），不持续虚构免费发货。
- 核心 GitHub Actions 已按该脚本执行；所有保守口径的统计均来自同一 `runAudit({runs:12,days:18})` 输出，不基于玩家手机截图、其它旧版本测试或理论推测。

## 2 实测：同资源条件，真正的岗位覆盖决定大多数失败
| 组别 | 成功上菜/晚 | 超时离席/晚 | 售出菜平均满意 | 利润/晚 | 实际回收/晚 |
|---|---:|---:|---:|---:|---:|
| 自动出餐（上限，非玩家操作） | 7.33 | 0.25 | 78.92 | 125.67 | 0.25 |
| 主厨右锅＋本地帮厨左锅 | 5.50 | 2.08 | 76.00 | 80.67 | 2.08 |
| 主厨在左锅与帮厨重叠 | **1.33** | **6.25** | 55.67 | 4.33 | 0.33 |
| 主厨停在传菜区 | **1.17** | **6.42** | 54.75 | -0.33 | 0.50 |
| 正常右锅＋已雇小羽跑堂 | 6.92 | 0.67 | 76.92 | 104.83 | 0.67 |
| 正常右锅＋两位当地跑堂 | 7.25 | 0.33 | 77.67 | 103.33 | 0.33 |

均值来自真实脚本。不同组别的员工工资与赠予充足食材的成本未被当作完全同等现实投资条件；与自动出餐相比，`walkable:true` 有实际物理移动与传菜工作。
- **右锅 vs 左锅**（完全相同 seed）：每晚多上 4.17 道菜、少 4.17 位客人超时，声望变化平均改善 9.33；右锅 vs 传菜区：每晚多上 4.33。
- 左锅组 `POT` 料理的超时平均 5.92 单、未经开火的超时订单平均 4.92 单，符合两厨位无人照看且空闲帮厨不跨位的源码逻辑；并非一个“食客不喜欢单一菜”的问题。主厨如果恰好站到帮厨已覆盖的 WOK，另一个 POT 物理岗位无生产速率。
- 小羽的首次雇佣令上菜多1.42、少超时1.42；第二跑堂仅再多0.33，且其工资导致利润未必更高。不要无条件让玩家先付55金币买第二跑堂来掩盖基础操作问题。
- 正常双厨位＋充足食材时，已售出顾客口味平均匹配 >91，品质84，平均满意约76。**不能从此推断所有玩家的低满意都不是菜单所致**：这是人为解锁的精选菜/足量原料控制组，只能证实其中占比最大的瓶颈是两厨位覆盖与等菜。

## 3 市场与一次真正赚得的旧店出口
| 配置（6种子×18天） | 每晚售出 | 每晚缺料拒绝 | 每晚超时 | 平均满意 | 每晚市场采购件 |
|---|---:|---:|---:|---:|---:|
| 只通过云港真实市场采购，不做外出探索 | 6.28 | 2.69 | 1.93 | 77.66 | 14.06 |
| 相同条件，另有原店真实营业赚来的一箱旧料8份 | 6.26 | 2.63 | 2.00 | 77.69 | 13.86 |

- 一箱累计平均带来的 **18日售出差异为 -0.33 单、期末现金多13.33**，受样本、库存、顾客离席与菜谱固定影响很大；不能直接宣布“进口无价值/售价应该减少”，更不能推断真实探索状态下的利润。
- 两组真实现金未出现负数（老店起始/新店起始条件和菜单都被人工选择以隔离机制）；市场采购缺料仍客观存在。若实际探索向当地仓库提供食材，玩家可能比无探索市场组更好，需下一轮真实探索结算对照。
- 本实测仅**一次真实旧世界售出生成的券**，不能替代计划中的每两云港日真实旧仓储托运。后续托管必须从旧仓扣出且给云港真实入账，不能把天然十几日免费送货当标准当前规则。

## 4 明确优先级（来自结果而非猜测）
**P0 v0.15-D.1**：云港两个真实厨位时，当本地帮厨空闲而另一工位有工作、且玩家不在那里时允许帮厨跨厨位支援，走2秒、无法同时两锅工作，禁止 Hearth 旧世界或评星阵容意外修改。优先让两锅能实际运转而非整体延长客人耐心。用相同12 seed复测 right/left/pass 的送餐、售出、工资、旧星章，不凭空增加员工。
**P1**：优化新手经营时可理解的员工/主厨站位说明（玩家需要知道谁在做哪口锅）；测试物理手机触摸再决定是否新增提示。
**P1 v0.15-J**：真正旧仓扣货的有限商船物流和留守经营需独立数值规格；再用真实多日对照量化稀缺与料理多样性。
**P2 v0.15-K**：镜露花园/新特产/新菜作为内容差异化，不能替代当前人手错配 Bug 的修复。

## 5 结果边界
- 全部测试只基于真实仓库源码运行的 Node 规则与模拟策略，不是录制真人手指动作、设备 CPU/帧率或手机 Safari 验收。
- 审计自行授予基础 cloud 菜谱/初始预算是外生条件；不声称当前新手一进云港即可在游戏中点选这些食谱。没有假造本地材料探索实际掉落，也没有连续自动托管赚货。
- 12、6 个种子样本能够确证岗位覆盖的方向性故障，但不足以为全局经济长期最优求解，需真机反馈和更大样本。
- `PROJECT_STATE`、`ROADMAP`、`START_HERE` 将按本次纯审计和后续修复分别更新。
## 6 P0 修复后同种子复测（实测，Cloud 双炉帮厨跨位）

已先提交 [v0.15-D.1 实现规格](V0.15D1_TWO_STATION_SUPPORT_SPEC.md)，后在未合并 PR #93 的引擎增加**仅云港两厨位**：空闲帮厨在另一厨位有真实订单且玩家未在那处时，走3真实营业秒后再工作，行走时原位置无工人且不能同时做两锅。旧世界双厨位、已经做菜的工作任务、工资、库存/售卖账本均不改。新增 3 项专项回归（离开原站、角色不传送、旧世界不受影响）。

**运行证据**：同一原始12个 seed的 GitHub Core workflow，完成新功能的中间 SHA `6e02f463`（引擎实际已含双炉支援，输出标题版本尚保留 alpha.9；后续正式版本设为 alpha.10）执行真实审计数据。563/563 Node 通过。与前文 alpha.9 正式原规则成对比较：

| 相同初始菜单、客流和100份外生原料的服务组 | 修复前售出/晚 | 修复后售出/晚 | 修复前超时/晚 | 修复后超时/晚 |
| --- | ---: | ---: | ---: | ---: |
| 主厨左锅（与帮厨重叠） | **1.33** | **5.17** | **6.25** | **2.42** |
| 主厨传菜区（两炉依靠帮厨） | **1.17** | **4.08** | **6.42** | **3.50** |
| 主厨正确覆盖右锅 | **5.50** | **5.50** | **2.08** | **2.08** |

- **可验证改善**：主厨留在左锅时，每晚多3.84份真实售出、少3.83人超时；独立烹饪者照看右锅时没有因为支援 AI 增加无效走位。没有更改顾客耐心和出餐数值，这是实际空闲帮厨从 WOK 走到 POT 并使 POT 不再整晚停工带来的增益。
- **仍有操作空间**：主厨在传菜区时仍比左右人员覆盖差1.42份/晚；雇跑堂依旧有独立价值。每台厨具仍需要真实的人来劳动，而非两个炉台同时自动不停产。
- 市场供应实验的 `right` 组没有改变（6.28单/晚、2.69单/晚缺料拒绝），所以**新修复解决的是错误站位造成的生产死锁，而不是云港食材短缺**。这两个 P1 问题须分开。
- 本表来自 Github Core 563项 Node 的真实记录，正式 alpha.10 的完整 CI/手机 Chrome 和 iPhone 感受需要继续独立验证；绝不能把过渡SHA自带的版本字段当成最终 Pages 已经上线。
