# v0.15-A · 第一章第三星「万味会宴」设计规格

**状态**：设计已入仓，玩法尚未实现；数值为待校准目标，不是当前游戏规则。  
**基线**：2026-10-19 的 `main`，v0.14.0-alpha.5。  
**关联**：[START_HERE](START_HERE.md) · [ROADMAP](ROADMAP.md) · [阶段规划](NEXT_DEVELOPMENT_PLAN_2026-10-18.md) · [P1 结果](V0.14F_P1_ECONOMY_RESULTS.md)

## 1. 要解决的体验

玩家反馈当前内容约十几游戏日、现实一小时内可玩完。第三星应在这一段旅程末端给出一次鲜明的章末考验和接下来的可玩目标，不用机械增加等待天数。首星已考综合评分；二星已用两夜考接待/利润和满意/菜品/协作，不能把第三星做成分数更高的第三场普通营业。

本章主题暂定「万味会宴」。核心是提前知道三位评鉴食客的不同口味，用现有探索、采购、研发、三道菜菜单、预制与厨位准备一晚真实营业；评鉴席在餐厅真实到店、排队、落座、下单、做菜、扣料、收款及评价。结果逐席反馈，玩家看得出是菜单不合口味、缺料、等待还是出品出了问题。名称及对白可在实现前润色，不改变规则。

## 2. 解锁、报名和晚间流程

| 环节 | 设计 |
| --- | --- |
| 出现 | 获得第二星后，从**下一营业日**的预告/备餐可看到邀请；没有另设“第 X 天”硬门槛、烤架/三厨位购买门槛或稀有 Boss 材料门槛。自然目标是约第 10–15 游戏日能尝试，实际取决于玩家进度。 |
| 预告 | 展示三位评鉴席的口味倾向、可接受价格范围和到店波次；从现有六类食客中选有区别的三类，例如家常、蔬香、尝新。具体三类组合由早期流程与菜单覆盖核验后冻结。 |
| 报名 | 仅在开门前主动预约或取消，保留现有库存、工资、市场、宣传和三菜菜单决策。无需另开料理小游戏或押金。每个营业日最多一次；失败后次日可再报名。 |
| 当晚 | 预定三波现有自然客位为评鉴席，不凭空增加总客流、座位或收入。客人走现有到店/点单/排队/离店链路；不会强行生成一笔已成交订单。报名、三席身份、偏好和到店波次随营业快照冻结，刷新不重抽。 |
| 中场 | 沿用现有可调整一次菜单的休息时机；换菜只影响尚未下单的客人，不追改旧单。评鉴席等位或离开也算实际结果。 |
| 日结 | 展示三席分别“满意完成／未完成”的菜品、满意度和原因，再展示会宴结果及一般营业账本。失败不回滚收入、材料、工资、XP或关系。 |

偏好提示要足够让玩家备菜，但不公开或操纵下单结果。实际点菜仍由当前菜单、预算、口味、库存及既有订单机制决定；若现有选择算法无法让三席公平覆盖可行菜单，先在同种子验证后调整**评鉴客点单选择**，不得在日结时伪造成功。

## 3. 通关判定与策略空间

采用可解释的条件，而非另一套 0–100 加权总分。以下是**第一版校准目标**，正式数值需在真实早期存档和同种子回放后写回本规格：

1. **食客认可**：三席中至少两位有实际 `status=served` 的原订单，且各自真实满意度 `sat >= 75`。未入座、缺料拒单、等位离开和做完但不满意各给不同原因。
2. **整晚撑住**：实际总成交至少 6 单，营业利润 `profit >= 0`。使用现有包含耗材估值、工资、活动费用和其他营业支出的日报口径；采购的现金流仍只在现金净变化里记录，不二次扣利润。
3. 两项同时满足才授星。没有“研发任意烤菜”“售出指定稀有菜”“全员满级”“三种菜都售出”的暗门槛。准备充分的双炉、三炉混搭、烤架路线至少两条应可过关；烤架可以提供不同的菜单策略，但不作为通行证。

评鉴客不是固定必买预制套餐；如果他们实际点了普通菜，就按普通菜评价。三席中的一位失败仍有挽回空间；若全靠某一随机到店时点决定成败，需要调整波次而非给玩家免费补单。两项经营门槛必须经第 10–15 日可达存档重新校准，尤其不能拿 P1“已学会 21 菜、500 起始币、固定 85 品质、21 天经营”的乐观中期模型冒充首次通关实测。

## 4. 奖励与传送门发布边界

成功授予本章第三枚万味星章，并解锁**第一扇真正可进入的异界传送门**。星章记录和下一章入口是同一里程碑：正式发布满星时，门至少已能完成一次探索、撤离带回材料、研发新料理、上架、客人真实点单与营业日结。门后的完整章节另用独立规格界定主题、内容数量和跨章存档；此处不预先承诺多个世界或大体量长线。

开发时可先在分支完成三星逻辑，再与首门最小可玩切片联合发布；不把第三星和一个空门或仅写“敬请期待”的入口作为正式奖励上线。既有两星存档进入新版本后保持两星，次日可报名；已有三星存档之后进入门时不得再发一次奖励。未获得三星仍可继续旧区域探索和旧食堂经营。

## 5. 状态、账本与 UI 接入

- 延续 `chapterProgress.chapterId='hearth'` 和既有一、二星状态，星数上限扩至 3；新增 `thirdAppraisal` 仅存报名日、最后尝试日和最近结果。旧档缺字段时补默认值，不覆盖一二星或旧正在营业的服务快照。
- `createService` 冻结是否报名、评鉴席身份与波次、菜单/厨位/宣传的现有快照；`closeService` 只从该服务的真实 `orders`、`events` 和既有 `profit` 汇总判定。重复日结和读档不能重抽席位或重发星。
- 授星用唯一账本键 `chapter-hearth-star-3`；传送门资格从已授三星记录读取。下一章进度另设章标识，不能把 `hearth` 的三颗星归零或写到新章里。
- 备餐页现有星章卡替换二星完成后的静态文案：显示报名入口、三席提示和最简两项条件。日报紧邻现有评鉴回执显示三席结果；320px 短屏先给结果和可行动原因，细节可展开。不可因叙事额外塞入大面积设定浮窗。

## 6. 实施拆分与验收

1. **早期进度基准**：用真实新档/代表性玩家路径记录首星、四桌、二星、可尝试三星的游戏日、现实耗时、菜谱、库存、金币及厨位；样本和玩家主观体验分开记。先确认“下一日可报名”不会把阶段推到一小时之外的纯等待。
2. **会宴规则与数据**：编排三席及波次，建立可复现的订单/结算对照。对双炉、三炉、烤架与不买烤架、低库存、报名取消、失败重试跑同种子多种子分布；阈值须让两种以上合理策略可过，同时不能只靠预知 RNG 或免费补料。记载通过率和失败原因，不用单一平均分代替。
3. **首门联动发布**：在门的独立设计稿及首个可玩闭环具备后打通解锁；按上述发布边界决定同一发布批次。未完成门前，三星功能保持开发状态。
4. **回归**：旧两星/一星存档、已开始普通营业快照、报告重复生成幂等、真实订单唯一扣料/收款、未入座/拒单/弃排原因、跨日重试、离线单文件、320/375/390px Chrome 的报名与日报。iPhone/Android 的中文字形、触控和节奏单列玩家验收，不用 CI 通过代替。

## 7. 待校准与非范围

**待校准**：三类评鉴食客及预算、到店波次、`sat 75` / 6 单 / 非负利润的可达性、是否有不合理的低库存 RNG 极端、首门具体主题与内容数量。必须在实现 PR 中回填数据和最后采用的参数。

**本规格不做**：新厨具或必须购入的扩建、免费食材、保底销量、无订单的剧情销售、二星第三夜、高分数门槛叠加、强制新手引导、多扇只有场景没有经营闭环的门。
