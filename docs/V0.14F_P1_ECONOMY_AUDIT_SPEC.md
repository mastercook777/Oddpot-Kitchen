# v0.14-F / P1 · 现行多日经营经济审计规格

**状态**：已确认待实施（审计，不修改正式游戏规则）  
**基线**：`main` v0.14.0-alpha.5，PR #75 已合并；历史结果见 [v0.13-G](V0.13G_ECONOMY_RESULTS.md)，下一阶段方向见 [开发规划](NEXT_DEVELOPMENT_PLAN_2026-10-18.md)（规划 PR #76）  
**目的**：分清食材供给、菜单选择、厨位产能、烤架成本和营销转化各自造成的真实经营结果，为下一项玩法切片提供证据。

## 玩家问题与本轮边界

现有十道烤菜、三炉通用烤架及 Lv2 升级已经实装。玩家能感知到烤架和爱肉客点单，但尚不清楚多日采购、探索、换菜单与工资叠加后是否值得投资。此前 21 日审计发生在 alpha.6、烤架前；不能把其缺料率、宣传回本和第二星通过率直接当作 alpha.5 的结果。

本轮只增加可复现的模拟脚本和审计报告；不改变菜谱、市场、掉落、星章、厨具、客人或存档，不提升版本号。没有新 UI。

## 实验设计与数据口径

1. 从同一组种子创建当前双星、四桌的中期店：500 金币、八种普通原料各 3 份、两名原有员工已雇佣，三炉组另有小炭和第三厨位。历史购置成本作为此前投资，单独列设备回本而不混入营业利润。每组至少 32 种子 × 21 天，关键单夜隔离至少 80 种子；每项对照的起点、质量、排班、主厨位置一致。
2. 每晚走真实 `ensureDailyMarket`、`purchase`、`createService`、`tick`、`closeService`、`advanceDay` 与唯一销售账本。八选四、单品初始 6–10 份、售价/预算、库存消耗、工资和宣传保持正式规则。营业利润使用报告里的 `profit`，现金另算；采购款不得二次从营业利润中扣除。
3. 固定菜单与每日按库存/市场选择可做菜的策略并排。动态策略只能在**已经学会**的菜中取三道，购货预算相同，不预知次日上架、不凭空补料。记录可做份数、实际选择、缺料拒单、实际销量、队列流失、营业利润、现金和期末存货。若动态组取得优势，报告其策略成本与客群失配，不把算法称为玩家真实操作。
4. 三炉普通、已购烤架 Lv1 和 Lv2 使用真实炉位覆盖、`recipeVariants` 与点单。比较同一客流下的混合菜、爱肉组合与素菜组合；显式拆分 180 金币购买和 90 金币升级、每日员工工资。不同菜单造成顾客的**菜品选择**变化，应标出，不能说所有条件完全一致。报告平均和 P10/P50/P90、实际成功烤菜订单、增量利润和累计回本比例。
5. 当前营销与自然经营比较真实计划到店、实际到店、完成、宣传收入与扣费后利润；营销因余额不足回退自然经营时应单列，不能算一次成功宣传。二星两夜在 alpha.5 重新抽样，不仅报告通过率，还要列低库存、双炉/三炉和菜单情境。
6. 真探索供给另列：只有能可靠执行真实地图、移动、交战、拾取、背包、HP、撤离、结算全链路时才称为“探索净收益”。若本轮没有可复现控制器，则用真实地图生成器统计静态资源的**潜力**，并将外生“每天额外 8 份”的旧敏感性组单列为假设。两者均不得冒称玩家实战收益。

每组保存种子和每夜核心指标；结果报告给出均值、分位数、配对差值和至少一个反例。明确模拟策略的限制：没有真人探索与主厨手动救场，策略选择不代表玩家一定会如此操作。

## 实施入口与验收

- 新脚本在 `scripts/`，直接 import `src/engine.js` 与 `src/data.js`；沿用 `simulate-economy-v013g.mjs` 的经营夜循环，避免复制或修改营业引擎。较慢的全量审计只作为手动或独立 CI 命令，短种子 smoke 校验保证能重复运行。
- 不能通过直接把 `kitchen.grillOwned` 标成 true 来伪装“实际已购”经济；建立有偿购买与开局已购的清晰口径。已开始营业保留快照，升级仅影响新营业；同种子重复运行结果一致。
- 核对 `sale` ledger 数量与已售订单、市场实际四项与采购量、菜单工作台覆盖、升级/营销交易不重复。脚本无对正式源文件和用户存档的写入。
- 结果文档列完整命令、代码 SHA、样本量与未覆盖项，随后更新 `ROADMAP.md` 和 `PROJECT_STATE.md` 中的审计状态。自动审计不等于手机主观体验；P0 实机另行验收。

## 审计后决策

若固定菜单导致缺料而动态换菜单显著改善，优先做备餐决策反馈；若真实供给依旧无法支撑新炉位，再设计供给修整；若烤架或营销回本不足，先分析原料与产能限制再调整单个参数。上述都是待结果决定的候选，不在本审计中偷改正式经济。
