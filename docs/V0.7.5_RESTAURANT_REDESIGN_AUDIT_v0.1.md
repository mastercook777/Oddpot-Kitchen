# 《怪味食堂》v0.7.4 不通过复审与 v0.7.5 经营系统重构规格 v0.1

**日期：2026-10-11 · 状态：REJECTED / NOT ACCEPTED（用户明确未通过验收）**  
**依据：** 用户正式版试玩反馈 + 当前 \`main\` 中 \`src/app.js\`、\`src/scenes_v04.js\`、\`src/engine.js\`、\`src/walkable_restaurant_v07.js\`、旧/新餐厅 CSS、测试。  
**边界：** 这是审查/改造规格，不表示缺陷已经修复。独立 v0.7.3 Lab 的移动和工作分工体验有一定成立依据；正式 v0.7.4 的画面、UI、交互流程和节奏没有达标。**不要在这轮复审里一边审查一边继续叠功能。**

## 一、失败定性：融合的是规则，不是完整经营体验

目前同时存在三个互相冲突的交互范式：

- 旧 v0.5 经营：点选顾客 → 排队优先级/招待 → 固定底栏执行操作；双厨位持续自动营业。
- 新 v0.7 移动：主厨移动站岗 → 实物取餐上菜 → 员工分工 → 主动技能。
- 旧波次事件：定时冻结 → 点“经营事件”或另一个管理选项 → 选完 → 手动“继续迎客”。

**重构目标：一切日常操作归位到场景内（靠近自动工作）；非常规支援保留显式技能；跨波事件一次选择即继续；保留菜单 Build、员工职责和真实收支反馈。**

上一版完成 177 项单元测试，但主要证明数据函数和现有记账链路，**不能证明手机视觉布局、角色路径、输入与连续经营的体验通过**。

## 二、P0：未解决不得再次提请验收

### P0-1 真正重绘“可走动的餐厅”，而非在旧 UI 上叠 Canvas

**现状证据：** \`src/app.js/restaurantView()\` 仍创建 \`diner-top\`、\`diner-kitchen\`（含 \`cook-avatar\`）、\`service-counter\`、\`diner-tables\`、\`diner-floor\` 等旧 DOM。与此同时 \`src/scenes_v04.js/drawDiner()\` 又完整绘制墙、两个锅、柜台、桌椅和人物。CSS 再用 \`opacity:0\` / 旧按钮透明命中层来掩盖。Canvas 使用 \`translate(w*.095,h*.075);scale(.81,.82)\`，而 \`src/walkable_restaurant_v07.js\` 再用独立的归一化热点和障碍参数。

**必须做：**
1. 制作 \`restaurant_scene_v075.js\` 的单一物理场景配置：厨房左右工位 → 主厨可站的工作面 → 中央取餐台 → 实际可走的通道 → 1/2 号桌（各 2 个座位）→ 入口。使用同一个数据源计算绘图、碰撞、人物导航、服务热点和顾客/员工路径。
2. 移动营业时**只有 Canvas/一套主场景渲染家具和演员**；删除/关闭旧固定厨师和大面积透明 DOM 桌/锅命中层（备餐、预报可以继续借用同一新静态场景）。
3. 厨位设备外形和玩家站位应肉眼对应。工作点在锅具**可操作的一侧**，不能站在锅中心或墙里；端菜必须实际从中央出餐台拿起。
4. 场景按 9:16 手机一屏先设计，320×568 / 375×667 / 390×844 验证：锅与桌足够可辨、走道宽于角色碰撞体、两个桌位不被 UI 覆盖。HUD/安全区是场景布局约束，不能靠随机 CSS 微调抢空间。
5. 放弃把原固定主厨贴图用透明度遮住的做法。单一主角实例仅在正确层级绘制一次；厨具、餐桌、客人使用同一世界坐标。

**验收：** 将各锅/餐桌的屏幕中心、绘制坐标、服务区中心和碰撞范围做调试可视化；真机实走全图，无“看得到但碰不到”“可穿过画出的墙桌”。

### P0-2 拆除旧版底部指令式操作

**现状证据：** \`src/app.js/service()\` 在 \`walkable\` 模式仍生成 \`selectedOrderId\` 相关的「↑ 优先出餐」「选择客人」、\`toggle-service\` 大按钮和文字引导；\`restaurantView()\` 继续给桌位/厨位装 \`data-seat\` / \`data-station\` 旧按钮和透明命中层；\`src/diner_05c~05e.css\` 残留选择高亮、座位标签。移动版又在世界中放摇杆和特殊技能按钮，导致两种命令体系竞争。

**必须做：**
- 移动营业模式完全移除「选顾客」「优先出餐」「选择客人」固定底栏、旧金币招待顾客按钮、直接点击厨位查询等操作；旧自动模式兼容分支可以保留原操作直至老存档营业结束。
- 底部让位给**真实场景**，不留一块巨大的空 Dock。只保留上方紧凑一行「第几波 / 剩余顾客或已送达 / 当前精力 / 暂停图标」；最重要的经营目标可放可折叠的迷你进度标识。
- 新版日常服务：站厨位自动做菜、出餐台取餐、目标桌上菜。不自动花费精力。只有「🔥 全力烹饪」「💛 紧急安抚」作为玩家主动点击的临时技能（图标 + 消耗数字，支持 aria-label）。
- 不应让“查看详情”成为移动的必要前置步骤。需要认识顾客点单信息时，在实际桌面显示订单小菜品图标/耐心圈、在真实工位显示制作进度/排队数；长按可选作次要详情，**不能变回选中桌子才执行工作**。
- 保留的暂停入口放顶栏，不反复打断单手移动。

**验收：** 新开业后的屏幕上找不到旧「优先出餐 / 选择客人 / 经营事件 / 继续迎客」固定按钮；不点任何顾客也能完成所有基础工作。

### P0-3 波次事件改为“自动出现 → 单次选择 → 自动继续”

**现状证据：** \`src/engine.js/tick()\` 固定在 \`v.time===20/41\` 设置 \`breakAt\`，\`chooseServiceEvent()\` 只标记 \`breakUsed\`；\`src/app.js\` 需要 \`show-management\` 打开、\`data-choice\` 决策，然后另点 \`resume-break\`。现有 \`show-swap\` / \`show-prep\` 又与决策并行，构成三套菜单。

**必须做：**
1. 达到波次节点且场景允许结束当前交互时自动冻结 **整个服务**（客人耐心、厨房进度、角色移动、精力恢复都暂停），立即出现一个轻量事件弹窗，**不先要求点“经营事件”**。
2. 事件提供 2–3 个能看懂成本和结果的选项。玩家点击任何**可支付/可执行**选项后，在同一次权威操作中落账、记录选择、关闭弹窗并 \`resumeBreak()\`，**不再需要单独点击“继续”**。
3. 金币不足或不可用选项要提前灰掉；点击失败不能恢复时间，也不能扣钱。防双击必须以事件 \`wave\` 唯一键做幂等控制。
4. 波间「临时换菜/应急预制」先移出这一流程：优先融入营业前 PREP；若要保留为战术内容，须变为**某一波次事件的直接备选效果**，不能回到多级管理页面。游戏不能失去菜单 Build 价值，但不必保留所有历史操作。
5. 旧存档中已暂停在 \`breakAt\` 的人，应有安全迁移：自动进入新版事件选择或正常继续，不被旧 \`servicePanel\` 变量锁住。

**验收：** 事件从出现到恢复时间只需一次有效选择；每波花费/效果只计入一次；可在此时切后台并恢复，不会跳过事件或重复执行。

### P0-4 修复新旧订单状态表现不统一

**已确认代码缺陷：** \`src/engine.js/tableSeatState()\` 的占用列表仍是 \`entering/ordering/queued/cooking/flying/eating/review\`，**不包括** \`pickup/carried/delivering\`；但 \`seatOccupiedAt()\` 和 \`src/scenes_v04.js\` 已把它们视为现场顾客。结果是顾客还在等菜，旧桌位 DOM/状态可能显示 **0/2 人**，与 Canvas 场景打架。

**必须做：**
- 统一 \`OrderState\` 及 \`tableSeatState/seatOccupiedAt/visual occupancy/guest bubble/waitingRing/supply UI\` 的枚举和派生状态；\`pickup/carried/delivering\` 都属于“仍在等待服务”。
- 交付图标与目标桌严格对应；主角端盘时应看得出是 1 号还是 2 号桌的订单（可用桌面边缘高亮/小方向提示，不依赖人物头顶文字气泡）。
- 顾客流失时，待取餐/携带餐/小芽路线/被占厨位一并释放或报损，不留厨房死单继续堵站位；保留原有原料扣除与唯一 sale 事务。
- 两位同桌顾客必须分别保存订单和座位，不能因一份盘子被端走就把另一位标成已就餐。
- \`serviceSupplyStatus\` 需要展示“制作中 / 出餐台待取 / 主角正在配送 / 小芽正在配送”的有意义概览，而不止 queued/cooking。

### P0-5 整个服务过程必须共用一个时间基准

**现状证据：** \`src/app.js\` 在 \`setInterval(...,750)\` 调 \`tick(game,1)\`，营业和客人耐心每 750ms 前进 1 模拟秒；\`walkServiceHero()\` 则吃 \`requestAnimationFrame\` 的真实 \`delta\`，横/纵速度还基于两个不同的归一化轴；\`stepWalkableShift()\` 每模拟秒检测一次走近动作，立即取餐/送达，**没有复用实验版 0.38/0.50 秒的近身自动读条**。

**必须做：**
- 统一服务逻辑时钟 \`serviceDt\`：通过固定时间步推进订单和物理动作，动画以插值绘制；暂停/切后台/事件弹窗时所有工作和恢复冻结，重新开始不得补扣现实后台时间。
- 主角移动使用统一世界像素速度和真正的归一化向量（保持斜向不比直线快），不要将同一物理速度错误投射到不同手机长宽比；转向与移动动画帧率一致。
- 近距离正常加工连续，取餐和上菜需要很短的可见动作读条/手势反馈（候选 0.3–0.5s，待真机），同订单只触发一次；**精力仍只有明确点技能才扣**。
- 员工路径应以**真实位置和路程/预设路段时长**持续插值，而不是完成订单后重置目标再瞬移；端盘与送达必须对应动画生命周期。
- 若经营模拟时钟决定维持加速倍率，应由单一倍率驱动角色移动、厨位计时、顾客耐心，不存在主角一个速度、客人另一个速度。

## 三、P1：新体验成立所必需的内容与表现

### P1-1 厨房重绘建议

新布局先保持“两个厨房设备 + 中央出餐台 + 两张双人桌”，**不扩地图**。主要重绘方向：

- 左右工位画成有侧面/台面/把手的实际灶台（炒锅与深锅沿用 PREP 配置），在靠近人物一侧显示可见地面的站岗环。
- 出餐台是清楚的 1–3 份盘子可视队列，所端料理保留菜谱的基本外形/颜色/图标，避免所有菜都像一张通用空白盘。
- 桌位放在主通道两侧，椅子和客人尽量不互相遮挡；真实可走道路能够绕过桌腿，桌位接待/上菜服务点始终可触达。
- 角色统一 \`DINER_ACTOR_SCALE\`，不能为了显眼把主厨增大；主角可以通过服装颜色/地面小定位圈与员工区分。精力技能提示只用 icon，不用盖住人头的长文字。
- 单人做菜、阿火帮厨、小芽端盘/走回柜台都要有简短但辨识度足够的动作。角色面向至少左右/上下的合理方向，不可所有移动方向都永远面朝同一侧。
- 明确绘制层序：地面/建筑 → 家具背面 → 位于同一深度的角色/盘子按 Y 值排序 → 家具前缘 → 轻量图标/UI，保证不穿桌或“飘在桌面上”。

### P1-2 视觉反馈代替旧管理面板

- **锅位**：工作进度小环、当前菜的缩略图、积压单数/缺料 warning。厨房空转需要肉眼可见，站位后立即让进度动起来。
- **柜台**：待取盘子与对应桌号的颜色/符号；取餐时盘子从台面消失并出现在主角手上。不要突然凭空端出同样的料理。
- **餐桌**：等待耐心渐变圈、菜谱小图标、即将超时警示；主角携菜时高亮目标桌。站错桌轻反馈，不强制弹出提示文字。
- **顾客**：真正“等待、焦急、收到菜、吃下、点评、离开”的动画状态，不靠跳出的抽象数值替代。
- **HUD**：第几波/到店&完成数/精力条/暂停，若确有紧急缺料，可使用短暂 toast，平时不遮挡世界。
- **日报**：保留菜谱×工艺对销量/评价/利润的解释，还要能展示主角亲自送达、阿火完成单数、小芽送达数量，避免工作策略和结果脱节。

### P1-3 主角精力与员工成为真实运营选择

- 阿火接手的是一个站位的基础加工；小芽接手的是取餐、送餐与稳定服务。招聘后玩家可以更自由地完成**高价值行动**，不强迫重复端盘以维持可玩。
- 保留“正常做菜/取餐/上菜免费；全力烹饪/紧急安抚必须主动点击”。
- 精力 UI 要清晰但不占画面；不同角色不因放大/满屏文字获得信息优先级。
- **单人首日可完成**：不要把压迫感等同于大量丢单；保留单人忙乱，但至少给予初学者可学习的时间、适量客流和可靠的低速自取保底。

### P1-4 区分“日常营业”与“经营决策”的两种节奏

- 正常营业：自己选优先做哪口锅、什么时间送菜、哪桌值得安抚。这些选择来自看懂场景，无需专门“调整优先级”按钮。
- 重大事件：波次提示直接选，选择后继续；若没有值得玩家决策的选项，不要为事件强制打断流程。
- 营业前：菜单 Build、预制、锅位设置和雇佣员工的高层管理集中在 PREP，不挤进移动营业触控面。
- 结束后：以可解释的日报连接“菜谱研发→工艺选择→实际经营结果→明日调整”。

## 四、P2：通过 P0/P1 后再考虑

- 主厨工作餐让特定 **菜谱×工艺** 增加精力或短时运营技能；不能在路过时自动花精力。
- 装备最多两槽先做差异化（鞋 / 围裙 / 服务饰品），暂不扩成多维 RPG。
- 更大的餐厅、更多员工、装修经营、批量端盘、AI 顾客路线扩充，全都后置。**先保证小餐厅单人到双员工完整体验。**

## 六、正式的发布 Gate（任何一项失败，不允许再称“通过”）

- **G1 操控与世界：** 320×568、375×667、390×844 三尺寸，主角/阿火/小芽/客人大小一致；走厨房→取餐台→1 号桌→2 号桌→厨房不会穿家具、闪现或被按钮偷指针。
- **G2 操作范式：** 无旧顾客选择/优先级/金币招待底栏；移动/基本工作自动，精力技能不自动触发。
- **G3 临时事件：** 自动出现、一次有效选择、自动恢复，无“经营事件→选择→继续”三级点击。
- **G4 连续订单：** 两位同桌、两个不同厨位同时忙碌、主角/小芽抢单、端错桌、顾客超时、预制菜、缺料，身份/显示/库存/营收一致且不会重复。
- **G5 员工价值：** 0/1/2 员工能稳定跑完整晚；独自经营有压力但可理解、有成功空间；招聘能明显减负，而不是替代主角放大数字 Buff。
- **G6 游戏核心：** 研发工艺/菜谱 Build 的真实制作时间、售价、口味适配和顾客反馈不退化；研究结算和员工餐/探索便当完好。
- **G7 存档：** v0.6.3、v0.7.4 正在营业中的存档不会卡死或重复扣款；跨天恢复一致。
- **G8 真机：** 单元测试和 GitHub Pages 部署成功之外，**必须额外做真实移动/触控与连贯场景的人工验收**，否则只能称“代码通过”，不称“版本通过”。

## 七、对旧 GDD 的变更备注

\`GDD 02 · 餐馆经营与菜单 Build v0.1\` 原本把“自动制作 + 固定底部指令”和“不要求逐份端盘”列为 MVP。此后玩家明确选择 **My Perfect Hotel 式角色移动、单人后厨值守、亲自端菜并自动交付、员工接管工作**，因此上述旧 GDD 的交互和非目标约束**已被项目后续明确决策覆盖**。但其中的三菜菜单 Build、客群需求、产能冲突、三波经营和解释性日报仍然成立。

建议重构验收通过后新增 \`GDD02 v0.7 · 主动经营修订\` 并从游戏总 GDD 引用；保留历史文档以追溯决策，不应让 Codex 按已过时的 v0.1 UI 重新实现“选中顾客→优先级”。
