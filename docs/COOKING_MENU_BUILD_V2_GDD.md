## 0. 共识与非目标
玩家已确认：取消可见料理评分；白/绿/蓝/紫/橙五阶；厨艺决定白至蓝，蓝开始获得词缀，词缀结果决定紫橙；词缀要具有暗黑式装备的随机、组合和数值浮动感；料理作为 Deck 单品，Slot 与 Cost 双约束；大师厨房开放第4槽；同菜保留有用的工艺版本；经营真实验证，而非仅看颜色。2026-11-27 玩家认可初版六系词缀池并要求落地文档。
本文的具体概率、阈值、数值范围、升级条件、锁定/去重规则等均为设计提案。不能宣称已平衡或已获逐项确认。
不做：独立装备洗练、付费抽奖、强制每日重复研发、重复刷同一菜作为主线门槛、无限词条库存、全橙毕业是唯一目标；不重写探索战斗、冻结主角美术、正式存档或原经济，直到对应迁移切片。

## 1. 产品循环与玩家体验
清晨看真实客群预报和库存→探索/采购→研发（可跳过）→保存工艺→构筑菜单（槽位/容量/厨具/库存）→备餐→真实营业→日报按工艺看收益与瓶颈→成长→下一日。
例：初级厨房7 Cost/3槽，研发一份橙色镇店菜（5）后可以带两道白色（1+1），也可改成蓝+蓝+白（3+3+1）；前者聚焦招牌，后者分散厨房负荷。若招牌订单过多造成等待离场，明天研发快手菜或换菜单。工艺永久掌握，营业的每份食物复制工艺，不反复随机鉴定；每一份仍需真实食材、真实生产与送餐，不凭词缀虚构交易。
玩家可主动寻找特定词缀方向，但结果有惊喜。白绿不是垃圾：低Cost、稳定、原有风味、真实材料需求；失败不是白色。收藏价值不等于最高色。

## 2. 品质判定与词缀生成
### 2.1 五阶契约
|品质|显示|基础厨艺|词缀|Cost（测试）|
|---|---|---|---|---:|
|普通|白色|合格|0|1|
|良好|绿色|良好|0|2|
|优秀|蓝色|优秀|1 普通|3|
|史诗|紫色|优秀|2 普通/高级，至少1普通|4|
|传说|橙色|优秀|2–3，其中恰好1传说，至少1普通|5|
失败（未知配方、漏投、偏生、焦糊等引擎判定不可售）不入收藏，不进鉴定，但真实扣料并解释原因。所有可售基础配方均可正常生产。蓝以上不附加独立全面售价/满意度倍率；白绿蓝可保留有限的基础熟度价值，紫橙继承蓝的基础值；避免原有 quality 与词缀重复计价。隐藏内部判定数据，不在图鉴、菜单、备餐、结果、日报、便当、评鉴展示料理分数；餐厅星评及客人评分是不同概念，保留。
### 2.2 基础操作（历史CB01过渡方案；下一版以第13节取代）
第一版复用 evaluateLiveCook/evaluateGrillCook 的真实可售、熟度、投料、技法、动作和历史内部评分，作为过渡判定：可售且内部质量<70 白；70–81 绿；≥82 且全部熟透 蓝（测试阈值）。逐菜、逐厨具审计可达性，保证不是仅某一固定动作序列才能蓝；若阈值与现行技法冲突，优先改为「全料熟透+至少一种有效厨具行为」等可解释判定，不强迫每菜爆炒。阈值只供验证，后续不同厨具规则有真实证据后再替换；不能误把历史最高分当本次厨艺。成功普通工艺是保底的经营起点。
WOK：真实下料、爆香提前、翻炒/颠勺；POT：投料、轻搅/收汁；GRILL：真实串序、火区、翻面、刷香料及正反面受热；STEAM：封笼、排汽。后续火力调节、锅内位置、分层蒸制等是独立机制候选，不是本轮必需，必须先验证词缀闭环。
### 2.3 生成器（提议）
输入 recipeId、vessel、实际食材、真实操作事实 facts、基础等级、真实已解锁能力、稳定 cookTxn。成功蓝级先从合资格普通池生成1条；再按合资格高级/普通及传说扩展池尝试追加。初始测试目标：完全合资格的蓝底样本约75%蓝/20%紫/5%橙；不是独立 roll 颜色再伪造词缀。具体可实现为：先检验合资格传说且未冲突的池，5%尝试1传说，追加可用普通/高级至2–3条；未命中传说后按20/95条件概率尝试第二个普通/高级；最终按真实词缀组合推导颜色，池为空或互斥则降阶，不强行补词。没有传说资格的样本实际概率可能不同，需按厨具/食材统计。普通蓝至少有一个可用普通候选（若池配置错误，拒绝配置/测试失败而不是静默生成空蓝）。
同一词缀类型有整数/百分比范围，初版均匀离散抽样（百分点或整数）；机制型固定效果/次数；不同时再随机层级和浮动大小造成多重极低概率。结果冻结：以世界/日/唯一事务/版本派生可重放的独立 RNG；成功消耗与词缀生成/入册原子提交；重复结算、刷新、重新打开结果不抽新词。禁止随机数依赖渲染帧数或时间戳；合法新一锅有新事务和新随机序列。禁止通过回读正在结算的存档零成本重抽。
### 2.4 可引导随机
基础食材/厨具/真实操作事实决定候选与权重，品质等级决定能否鉴定，实际操作不是唯一硬公式。建议基础权重1，合适行为×2，匹配食材×1.5（上限×3），多种操作均可通向同系，UI用「偏向效率/香气」不公开逐词缀精确概率。普通食材可出传说（至少有一条基础厨艺可达传说候选）；特殊材料/厨具只拓宽候选，不是橙装唯一许可。示例：翻炒、颠勺/均匀受热提高效率；提前爆香提高吸引；全部熟透、合适技法提高经济/服务；真实蒸、炖、烤工艺提高对应候选；罕见食材拓宽特殊词缀。不凭不存在的火力/位置读数造假。蓝底玩家反复研发仍消耗原料与时间；不强制每日多锅，后续可允许额外实验机会，单日次数、时间成本、保底由实际节奏验证。
### 2.5 互斥与预算
同 id 不重复；同一互斥 group 至多1条（time、prep、yield、price、refund、demand、patience、sat、loyalty、reputation、arrival、bento、energy 等）；同类数值不得在单菜内换名叠加。互斥不是跨全部菜一刀切；跨菜单/营销/客群原效果按明确 cap 结算。第一版每菜时间倍率至少0.75、售价最终词缀倍率最多1.30（传说特例需单独审核）、点单权重倍率最多1.35、额外满意度最多8、额外资源每订单最多一次（提议）。机制词缀与数值词缀合并受实际事件预算和防递归约束；稀有词缀不能绕过厨具、库存或桌位。优先上线直接数值类，复杂机制必须有真实事件钩子和回归才入池。

## 4. 菜谱与工艺收藏（装备化）
RecipeDef 保存固定配方、食材、基础售价/时间、原有风味标签和厨具；AffixDef 保存 id、阶、scope、group、roll range、资格条件、效果版本和显示文案；Variant 保存 recipeId、唯一 variantId、vessel、style、baseTier、rarity、affixes[{id,value,effectVersion}]、实际研发记录、来源 cookTxn、保留/锁定标记。食材风味不等同随机词缀，配方本身不变；允许以后开放食材替换，不作为本期前置。
variantId 必须与原 style-only ID 分离；同菜同技法不同词缀/数值仍是不同工艺。按 recipeId+真实配方/技法基线+排序词缀及数值签名去重；完全相同自动合并来源/最佳基础记录；同组同词缀严格数值支配且基础属性/Cost/条件一致时，提示替换而不无声删除。锁定、当前菜单、备餐、在途订单、便当引用禁止删除；达到暂定每菜12个工艺（含旧版）时让玩家选择保留、替换或放弃新结果（仍真实扣料），绝不自动删有价值组合。结果确认前可看已有版本对比；旧工艺继续可用，不需要每份手工重做。容量上限需经长期试玩校准。
颜色只表稀有，不作为自动替换依据；菜单选择明确到 variantId；图鉴按菜名/厨具/品质/词缀筛选，可快速对比基础成本、售价、时间与条件效果，玩家没有必要每天整理整个收藏。

## 5. 菜单 Deck 与厨房成长
|厨房阶|Slot 上限|Cost 上限（提案）|成长|
|---|---:|---:|---|
|初级|3|7|起始|
|熟练|3|9|容量成长|
|高级|3|11|容量成长|
|大师|4|13|玩家明确第四槽解锁|
实际星级/扩建门槛与价格另结合现有首星/二星/三星、云港经济测试；不把厨房阶直接等同物理厨位。第五槽、Cost减免、专精与显式套装共鸣后置；现有风味 synergyFor 不无故删除。Slot=可上架菜种上限，Cost=构筑预算，不是金币/食材，实体厨位=实际生产并发。第一版建议至少3道有效、最多Slot，允许大师选择3或4；禁止同 recipeId 重复（当前可重复会扭曲点单/共鸣，属新增提案，需兼容旧档）；不强制使用全容量；同一菜的多个版本不能同时上架。所有选择同时通过章节食材/配方、已拥有厨具、实际已配厨位、库存可服务预警（非全量强制备齐）与预算校验。开业必须真实具备最低有效供货能力，不可因预算迁移卡死。
13点4槽举例：5+5+2+1；4+4+4+1；4+3+3+3；5+4+3+1。7点3槽：5+1+1 或3+3+1 或3+2+2。低色应有实际客群/产能价值。大师仍不能全橙。
特殊菜单：现有 premiumMenu（额外特供、份数限制）不能变成免费第五槽。建议将特供作为一个已占用槽位的上架模式，正常计Cost，限量/溢价/稀有食材规则保留；迁移先保留历史在途特供订单快照，新的特供入预算。若用户希望特供独立，另定共享预算规则。现有 swapBreakMenu 波次换菜：不能直接绕过 Deck，保留事件玩法但只允许通过同一校验、对下一波生效，原订单/已制备份不重新定价；建议首版在营业中只允许已有合法配置的同配方工艺不变/合法换菜（不得随时换工艺），后续事件规则需核实。禁止绕过 UI 直接调用 engine 改 activeVariantIds。
开业后冻结 menuSnapshot（recipeId+variantId+完整词缀、条件值、基础售价、时间、食材、厨具、版本）。预制份按 variantId 记账，不能把低品质预制重新标成橙品；波次换菜不改已接订单，只新订单读更新后的合法快照；菜单变化后联动对未来订单重算，已产生订单保持原值。便当单独选工艺，不占餐厅 Deck Cost，但真实扣料，特殊词缀仅作用于真实支持的探索事件。

## 6. 经营结算与工程契约
基线源码：src/cooking_v063.js 有 LIVE_ACTIONS、evaluateLiveCook、resolveTechnique、makeLiveVariant；src/grill_cooking_v014b.js 与 engine 的 grill mode 有串序/火区；src/engine.js beginLiveResearch、finishLiveResearch、ensureRecipeVariants、activeRecipeVariant、chooseRecipeVariant、recipeCraftSnapshot、canMenu、selectMenuRecipe、prepStockForecast、premiumMenuActive、createService、customerFit、swapBreakMenu、closeService、prepareBento 等；src/app.js research、researchReceipt、grillResearch、菜单/备餐/图鉴；src/three_y4b_research.js read-only。现行 2–3 食材，实时最多19秒，动作各一次；原工艺会以 variantId/质量替换且最多8条；现行 canMenu 正好3槽、selectMenuRecipe slot<=2、允许重复；特供额外且波次可换。不能把这些基线当成新版已完成。
建议模块 cooking_affixes_v2.js（纯定义、资格、seed生成/稀有度推导、规范化）、menu_build_v2.js（纯预算/槽位/快照）、affix_effects_v2.js（纯效果解析与有状态事务事件钩子）、存档适配在 engine；所有效果先计算后真实提交，UI只读状态/调用权威操作。
结算顺序：合法菜单与可供料→客群原始风味/预算匹配→合法候选相对点单权重→锁定订单价格/耐心/工艺→真实工位生产（时间倍率及下限）→一次扣料/返料→真实送达与评价→一次销售/小费→日报。原 customerFit 预算惩罚仍有效；点单权重改变相对概率而非强制选中；若原算法为最高适配优先，需新增可重放的有限权重选择并审计原偏好，不能靠UI标签冒充真实权重。
词缀新增的经济交易/客流事件有稳定事务ID（orderId/affixId/triggerIndex），不能重复回收；机制额外顾客真实排队、不会递归、不能影响历史订单。评星不能由满意度词缀直接改评分门槛；只允许真实服务指标产生间接影响。原配方专属工艺的 guestFitDelta、timeDeltaSeconds、priceDeltaCoins 与旧 quality 价格需统一口径，过渡保留旧档订单快照，新工艺避免原加成和词缀同方向双计；需逐项审计后定兼容表。
日报至少展示每个 recipeId+variantId 的真实点单数、完成/离场、营业收入、实际耗材、平均等待/生产时间、词缀触发次数与实际收益（条件未触发明确显示）；可显示净额口径，但不可把估计节省时间/吸引权重当已赚金币。新旧工艺跨世界仍收藏；能否上架以当前章节真实配方和厨具/食材资格为准，不强迫旧章传说无效或跨世界导入不合法料理。

## 7. UI/UX（与场景优先 2.0 一致）
### 7.1 研发工作台
锅是操作主体，完整环境（木桌、灶火、备料盘）；顶端仅厨具、库存/退出等少量HUD。准备时选2–3食材，显示风味/耐热与潜在倾向；开锅后托盘→锅的点击/拖拽/手势，保留可点击辅助；各厨具真实特有操作，熟度以图标、颜色+文字/形状（色盲可辨）及音效/蒸汽反馈。不要为未实现的火力/温区画假控件。实时仅显示真实熟度、时间、已发生的行为与词缀倾向，不提前告知最终词条，不显示分数或概率滚屏；鉴定时才揭晓。小屏锅与控件至少44px触点，手指不遮关键反馈；离开/弹窗/失焦时按明确暂停策略处理，不损耗玩家未确认时间。
### 7.2 鉴定与工艺详情
出锅→基础白绿蓝反馈→蓝以上鉴定实际已生成词缀→最终色边框/名称/稀有度文字→菜品特写、Cost、厨具、售价/时间/材料→词缀及范围、条件描述→与已有工艺比较→保存/放弃或继续。跳过动画/减弱动态、重开不重抽、不用假出橙。失败给真实原因而非白色，历史操作复盘放二级窗口。研发、图鉴、菜单共用装备式详情；固定色阶白/绿/蓝/紫/橙，深浅对比清晰，同时文字标识，数值带单位；不要求每种颜色重画菜品。
### 7.3 菜谱收藏与菜单 Deck
餐厅菜单热点打开单一游戏窗口。顶部容量条 x/y、3或4槽卡（品级框、Cost角标、图标、选中工艺），底部按厨具/词缀/品质筛选的有限卡片网格/分页；点槽替换、点详情对比，明确显示超预算/重复/缺厨具/不可用章节原因；第四槽到大师才出现（此前只在成长目标提示）。选择后实时预算与设备负荷预估，未达开店条件禁开且解释；默认可用原低色组合，避免卡死。预制与菜单同工艺标识，营业锁定。原型验证320×568/375×667/390×844，无整页滚动，窗口内部允许有限资料滚动，图标、返回、焦点、触控、2D降级。独立 Cooking & Menu Build 2.0 工坊复用真引擎但隔离内存夹具，不写正式存档；测试用 seed 和概率预览清楚标注，正常玩家界面不出现调试控制。
### 7.4 成长与日报
厨房等级升级窗口明确 +Cost/+Slot，已完成购买隐藏；物理厨位独立，显示新设备适配。日报从真实运行解释“招牌太受欢迎→该炉拥堵”“快手→完成更快”，只展示实际观测与可核对统计；不生成伪造推荐数据。

## 8. 旧存档、跨章节与迁移
先读取现行 save/schema/序列化、章节切换字段与离线构建，禁止直接重置库存、金币、星级、菜谱、员工、历史订单。建议新 schema 标记 affixSchema=1（待代码核对），迁移幂等。原工艺保留 legacy 标识及历史质量/动作；迁移不随机发词缀，不伪造新发现。现有菜至少保留一个白色可用基础工艺（不消耗、不凭空加特性）；无词缀旧工艺可按白/绿映射并保留原历史属性的兼容快照（不能生成无词缀蓝/紫/橙）；若旧工艺原经济优于新版，先保留历史实际价值并审查 Cost/收益是否破坏平衡，再选择显式过渡，而非悄悄降级。迁移须展示一次清晰说明，保留可恢复原备份。
已进行中的研究/服务/备餐/特供/便当按原规则完成，不改变已报价订单/已扣料；在安全阶段边界启用新规则，旧预制不可冒用高色，旧菜单若重复/超容量/不可用则引导合法调整，初始白工艺与已有材料提供可开店路径；不自动吞菜/清库存。跨章节分别保存厨房等级/菜单预算及本地菜单，工艺收藏沿原有全局/本地字段语义迁移（须核对 LOCAL_CHAPTER_FIELDS），不跨世界绕过食材限制。旧回放、离线 standalone、缓存版本一并核对；测试/工坊不能覆盖正式 localStorage。

## 13. CB2-R · 研发体验专项（2026-11-27 玩家深度试玩反馈）
### 13.1 方向验收与范围

静态证据：cooking_v063.evaluateLiveCook 对受热中仅扣16而仍可售；baseTier 对全熟且任意动作直接蓝；GRILL 双面熟透必翻面，天然跳蓝。旧 quality 还按动作存在布尔加分。engine.finishLiveResearch 在consume后、入原recipes/variants前需要统一实验判定，否则会出现界面判失败却已发现菜。three_y4b_research 当前两层33/30ms节流（上限约30fps，非实测性能），烤串组位置按lane立即切换，翻面围绕轴，但无完整穿串、摆串过渡，刷料动作与串接触弱。以下为设计提案，不改正式代码。
### 13.2 厨艺判定：合格门槛与品质独立
- 硬门槛：配方合法、所有选定食材投入且全部熟透；偏生、受热中、漏投、焦糊、烤串任一面未熟均失败；真实扣料一次，不学习、不生成工艺/词缀、不进收藏。白是合格可吃的家常菜。CB2-R实验状态下权威引擎判定必须在研究完成写入学习/工艺前执行，避免UI事后否决；正式旧路径保持原行为。
- 品质不再沿用旧quality或任意动作存在判蓝。根据真实事件轨迹计算三类连续证据：食材投放协调/顺序、技术动作有效性与时机、起锅时的火候平衡。各厨具独立归一化，不以相同绝对秒数/动作计数套全部；必须动作（烤串翻面）不自动加到蓝。起锅在充分成熟且离焦糊安全的窗口表现更好；不同食材耐热差异、不同技法路线都能得到优秀；不强制全点按钮或背唯一固定序列。现有实时机制先打磨，新增手势/多次动作/移动火区作为后续候选，不同时全加。
- 初版测试模型（非定版）：三维约30/35/35，单维平滑0..1，归一为内部0..100；合格后以55/75为暂定白绿蓝分界；优秀要求至少两维有充分证据且无显著低项，不能靠某单维刷满。不同合理路径可达到蓝，白/绿也必须由真实熟透操作获得。基于实际轨迹与有限随机种子给予边界约±3以内微扰，确定性优秀/明显不足不跨级，失败永不因随机变成功；随机只在相邻边界且不允许明显差操作直接蓝。独立 seed/txn 流，刷新不重抽；词缀 RNG 独立。内部数值仅测试/debug，正式玩家界面绝不显示。
- 建议实测梯度：WOK 全熟但投料/技法不协调可白；合理协调且一次合适动作可绿；先爆香或按耐热顺序、适当翻炒/颠勺并及时起锅可蓝。POT 温和慢炖与浓香收汁为两条路线，非必须同时点；STEAM 成熟门槛、封笼与排汽时机、水分体验；GRILL 不将翻面本身视为优秀，双面均衡、不过火、适当刷料和串序/火区适配构成品质证据。示例非固定解。数据驱动热量/成熟窗可逐食材标定，以现有liveCookAmount/liveIngredientHeatFeedback/grillHeat为真实基础，必要时抽出共享归一化helper，不复制一套UI假温度。先以常用菜验证可达性再扩全配方。
### 13.3 一句话厨师提示
失败：明确实际失败原因，不隐藏可食门槛，如“牛肉中心还未熟透。” 白绿：只给一句由本次实际证据驱动的建议，选择最值得尝试的一项（若多个同等候选可seed选一个），不得报内部分数、具体秒数、加分表、唯一正确顺序、完整逐步复盘。例“香料的香气还没来得及融进主料。”（确实底香不足时）；“翻炒时食材还没充分受热，试着再等一会。”（真实时机偏早）；“两面都熟了，但一面火候明显更重。”（实际热量不均）；“菜已经熟了，继续加热让口感失去了一些鲜嫩。”（晚起锅证据）。无可靠诊断时泛化到真实现象，不捏造。蓝及以上主要展示成品和词缀，成功提示可选简短风味描述，不强制复盘；仍允许玩家自学规律。游戏内部开发日志保留完整证据用于调试，不在玩家界面泄露。
### 13.4 烹饪交互与3D表现专项
原则：把真实事件映射到持续动画和感官反馈，不由动画反向决定品质。锅/串/灶始终可见，HUD仅展示厨具、时间/状态、食材、操作。直接点托盘/可选拖拽下料；熟度反馈清楚但不把最优起锅点画成精确答案。动作按下立即有确认反馈，实际有效性由轨迹判定，输入不被动画锁死；视觉动效与模拟时钟分离，暂停/失焦/恢复安全；结果用菜品特写+色框+词缀+一句提示而非表格。连续研发快捷保留配方选择但重新耗材、重新操作。
- WOK：食材有真实落锅弧线、接触锅底弹动、油花/滋滋声、翻炒由锅铲带动，颠勺锅体抬倾→食材惯性抛物线→落回；待机不做无意义旋转；火候/颜色渐变与实际状态对应。
- POT：不同成熟阶段冒泡、汤面扰动、轻搅形成旋涡，收汁有真实液面与浓稠感；不过度复用炒锅抛掷。
- GRILL 优先重点：空签/备料区可见；点击食材时从托盘沿签轴依次穿入，食材中心与签轴一致、间距合理；整串抬起→移向所选火区→放下；串有可见木柄、两端穿出；翻面抓柄抬起并绕签轴旋转180°后放回，所有食材随同刚体旋转；刷料刷子沿串往复并产生局部油光/滴落/火花；正反面颜色基于实际累计受热区别，炭火/烟/焦边渐进。必须不是食材悬空摆放或烤架整体旋转。现有lane选择、单次翻面与刷料规则优先保留，先不强迫新增操作。
- STEAM：开盖/封笼有明确位移、蒸汽随盖状态变化、排汽喷散并逐渐消退，食材可辨。
- 渲染：去除不必要双节流，设备允许目标60fps/低性能稳定30fps；不能宣称真实帧率未经测量；按真实事件的连续时间插值，粒子池/材质/几何缓存、限制DPR与粒子数量，生命周期安全；记录代表手机帧时间/掉帧，备用2D有真实动作/状态，断网不白屏。音效作为提升感知候选，默认遵守静音/设置。动画若在低帧时缩短/降级不改变判定。四厨具视角和占屏需实际截图和短流程动图/录像验收，不以DOM尺寸代替视觉。
### 13.5 切片顺序及验收
R1 严格可售+连续质量+一句提示，先实际轨迹样本与测试；R2 独立工坊工作台UX、烤串专项动作/状态渲染，逐厨具打磨；R3 四厨具实玩、保留整晚闭环、词缀/Deck/旧正式规则回归，玩家复验。建议小版本递进，不一轮大改全部。第一版先验证研发乐趣，剩余16词缀与经营大改暂缓；CB3正式迁移继续等待研发通过。
验证每类厨具至少两道真实配方/两条有效优秀轨迹、全熟白/绿/蓝，失败覆盖所有欠火/漏料/焦糊/单面；动作过早/过晚/有效对照，起锅窗口与投料顺序对照；多seed边界随机只影响相邻档，清晰差/优结果稳定；100%蓝才能生成词缀、同txn重试不重复扣料/重抽；白绿可上架、橙紫源自词缀，整晚不回退。各等级自然可达而非刻意制造糟糕操作；不得用一个固定测试时序作为游戏唯一解。实际分布需实测校准，不预定总体比例。提示用测试轨迹验证因果与不泄露公式。三尺寸真浏览器空锅/实投/动作/结果/一晚、2D降级、旧回归；玩家主观确认操作与表现。本文仅设计，无新代码、测试或部署；具体权重、阈值、随机幅度及实现排期是待验证建议。
