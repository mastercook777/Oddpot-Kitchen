# 《怪味食堂》v0.6.3 · 料理工艺收敛与跨系统收益设计（讨论草案）

**状态：待确认的设计草案，尚未开发，不代表已经实装或平衡通过。**  
基线：GitHub `main` v0.5E.1 经营引擎 + 已验证有反复研发动力的独立 `experiments/v06-2-two-pots-cooking.html`。  
日期：2026-10-11。

## 0. 目标：不是更多烹饪动作，而是料理研发→应用→反馈→再研发

玩家已经认可「选厨具和食材 → 自由实时下锅 → 翻炒／颠勺或轻搅／收汁 → 根据投放顺序、动作和时间得到工艺词条」的基本体验。收敛意味着：

1. 不扩充基础厨具、操作种类、三段格子与 QTE。
2. **同食材、同厨具固定菜谱身份；操作改变工艺，不改变菜谱 ID。** 换厨具才可以改变菜名与生产工位，如牛肉+洋葱：炒锅「葱爆牛肉」，深锅「洋葱炖牛肉」。
3. 不企图手工数值策划 168 道菜。8 食材中任选 2–3，共 84 组合 × 2 锅具 = 168 组合身份；保留生成命名兜底，优先精制已有的 12 道及新增 4–6 道招牌菜与若干菜系模板。
4. 从本次实验中提取**一条主风格、最多一条辅助词条、一个最终品质值**。完整事件日志只用于反馈解释／图鉴／重放，不无限叠加增益。
5. 失败（夹生、漏料、严重焦糊）真实消耗试验原料、不可收录上架；稍欠火低品质可以收录。避免过高失败率。
6. 让每个工艺在上架经营、员工餐、探索便当三种用途里出现**可实际感知但有边界的收益**。同一次用途只消耗一份料理原料，不凭空复制实物。

## 1. 已实现基线 vs 尚未实现

| 领域 | 当前主线已实现 | v0.6.3 提案 |
|---|---|---|
| 研发 | 3×3/三拍热量 puzzle, `s.recipes[recipeId]` 只存最高品质 | 用 v0.6.2 连续实时代替；保存不同工艺及品质 |
| 菜谱 | `RECIPES` 12，道具最多 3 材，固定 `station,time,price,tags` | 主线 12 兼容；主打 16–18 招牌，其他采用稳定菜系模板 |
| 菜单 | 三道菜；`s.menu` 只存 recipeId | 三道菜不变，为每道菜指定当晚默认使用的一个工艺版本 |
| 厨房 | 双物理厨位 WOK/POT 可改装 Lv2；生产自动调度 | 选定工艺对单价、顾客偏好、耗时产生小幅变动 |
| 顾客 | `fit` 基于固定菜谱风味、定价；满意度基于 fit/quality/wait | 在固定基础风味上叠加受限的工艺修正，订单创建时冻结工艺 |
| 员工 | 阿火、跑堂小芽每天各吃一份扣真实食材；帮厨最大省 4s，跑堂耐心最大 +12s | 投喂明确的工艺版本；辅助增益不能突破旧上限 |
| 探索 | 每日先探索后研发，尚无便当系统 | 在次日 `forecast` 阶段决定携带并消耗已学料理，进入 `field` 才生效 |
| 账本 | `transact/consume` 幂等、顾客落桌才销售、评价后加口碑 | 不允许词条系统自行记钱、改库存或重新计算已经生成的订单 |

## 2. 统一数据模型

- `BaseRecipe`：`recipeId, ingredientSignature, vesselType, name, baseTime, basePrice, baseTasteTags, materialCost, curatedTier`。原 `RECIPES` 可经兼容解析器读取；不要在运行时动态修改原始常量。
- `CookVariant`：`variantId, recipeId, ingredientIds, vesselType, style, secondaryTrait, quality, valid, techniqueSummary, discoveredAt`。优先只保留「每种菜谱×主风格」的最佳品质版本；若辅助词条不同，允许最多两条额外收藏，避免背包爆炸。
- `activeMenuVariant`：`recipeId => variantId`。主菜单仍三道菜，同日换工艺可在准备阶段完成。已经点单的客人和已经预制的实物必须保存旧工艺快照。
- `CookEvent`：下料 `{ingredientId,t}`、动作 `{type,t,ingredientsAlreadyInPan}`、起锅 `{t}`，提供可解释的后端判定，界面不需要显示公式。

注意当前 `chili_meat` 允许 `beef+chili` 替代 `chicken+chili`，但旧菜谱原料表仍是 `chicken+chili`。集成时必须把**实际实验使用的食材签名**放进版本/配方实体，否则研发用牛肉、营业却扣鸡肉。旧存档兼容策略要写专项测试。

旧 `s.recipes[recipeId]=质量` 映射为 `legacy-standard` 默认工艺，保留原售价、工时、解锁、员工餐与菜谱三格。新字段以可选字段迁移，不要求强制清空已有存档。

## 3. 主风格与实际经营收益：第一版候选数值

下表均为**初始平衡提案，非已实现数值**。品质最大继承原主线保存上限 90；操作判定成功不再额外给无边界多层品质分。

| 主风格 | 适用厨具 | 上架经营 | 经营取舍 |
|---|---|---|---|
| 家常 | 炒锅 | 生产时间及价格不变；优秀熟度的保存品质可额外 +2（上限 90） | 稳定、但缺乏专项加速和高价 |
| 爆炒 | 炒锅 | 制作时间 -1 秒；冒险者/评论家适配 +6（只在他们喜好与菜品口味匹配时） | 快速出餐，可能牺牲特定客群覆盖；品质不享受家常奖励 |
| 香味十足 | 两锅 | 对匹配「香/甜香/菌香」口味的客群适配 +8；出餐时间 +1 秒 | 较高评价潜力，以吞吐换收益 |
| 家常炖煮 | 深锅 | 生产时间及价格不变；优秀熟度保存品质 +2（上限 90） | 稳定型，非高价或快出 |
| 清润慢炖 | 深锅 | 家庭/街坊食客适配 +6（基础风味也需匹配）；时间不变 | 覆盖温和客群，仍需正确菜单配置 |
| 浓香收汁 | 深锅 | 售价 +2 金币；制作时间 +2 秒 | 单单高收益，客流高峰时更容易排队 |

示例（**沿用主线已有定价与时间**）：
- **焦香蒜牛**原价 32，炒锅基础 9s：家常 32 / 9s；爆炒 32 / 8s；香味十足 32 / 10s（附适配加成）。
- **蘑菇焖鸡**原价 24，深锅基础 12s：家常炖煮 24 / 12s；清润慢炖 24 / 12s（偏好提升）；浓香收汁 26 / 14s。
- 只有当工位开工才消耗对应 `variant.ingredientIds`；售价仍是菜落桌的**一次性**入账，评价仍由真实顾客状态确定。

计算顺序建议：
`baseTime + styleTimeDelta - levelBonus(每级-2s) - helperBonus(旧上限4s) - eventBonus`。给最终最短时间设置 **3s 保护下限**（需和现有测试比较，不能直接修改旧订单表现）。工艺不应无视锅具覆盖或突破两个实体厨位的并行约束。
顾客偏好不能简单把新词条直接塞进 `CUSTOMERS.likes` 重复获得固定标签的 +20；应该作为单独的、最多 +8 的适配调整项（`clamp(fitBase + variantFitDelta,0,100)`）。

## 4. 员工餐收益：沿用两人和原有上限，不再叠叠乐

现有算法：阿火基础省 1s；辣味+炒锅额外省 2s；菌香+1s；品质≥85再省 1s；总最多省 4s。小芽基础耐心 +3s；温和+6s／菌香+4s／其它+2s；优秀品质+2s；总最多 +12s。这里也有三日熟练的微成长。

工艺作为**小幅修正**并纳入旧总上限，不重写旧 Base Taste：
- 阿火吃「爆炒」版（在炒锅岗位）→ 额外 -1s，每单合计仍 ≤4s。
- 阿火吃「浓香收汁」版（在深锅岗位）→ 额外 -1s，每单合计仍 ≤4s。
- 小芽吃「香味十足」或「清润慢炖」版 → 当晚耐心再 +2s，总计 ≤12s。
- 小芽吃「家常/家常炖煮」版 → 耐心再 +1s，总计 ≤12s。
- 原有每日每员工至多一餐、投喂扣材料、员工餐成本计日报、熟练度上限和营业快照一律不变。

**防止虚假增益**：UI 显示「预计：阿火当前省 3s → 投喂后达到上限 4s」，不要只写「获得 -1s」而实际已经满上限却没有变化。

## 5. 探索便当：只做一个食谱用途 + 一次有效触发

因相位为 `forecast → field → research → menu → prep → service → ...`，探索 Buff 必须先于探索阶段发放。

建议 `forecast` 页开放「今日便当」：选择**以前已研发并可用原料制作**的一个版本→准备便当，使用专属当日幂等扣料 `bento-{cycle}-{day}`→进入探索后一次生效。当日研发出的新菜下一天才能带出去。第一天允许用开局自动解锁的基础料理制作，不要求强制带饭。一天最多一份。

第一版只做四类感知明确的作用，并只应用一种：
| 工艺风格 | 便当效果提案 | 触发约束 |
|---|---|---|
| 爆炒 | 「热血便当」本次探索移动速度 +8% | `stepActionField` 读取现场快照，最大只增加一次属性，不得连续加倍 |
| 香味十足 | 「寻香便当」第一次合格采集额外 +1 单位 | 必须遵守单堆最多 3、背包容量以及探索结算账本；满时不触发额外份 |
| 家常/家常炖煮/清润慢炖 | 「暖胃便当」第一次真正受到伤害时抵消 1 点 | 不能在 `settleField` 后再恢复生命、不能重复抵消 |
| 浓香收汁 | 「回气便当」本次探索第一次血量降到 1 时恢复 1 点 | 最多一次，生命不能超过当前最大值 |

跨系统收益不等于所有效果同时生效。研发永久解锁一套工艺，但**每做出一份实物，只能用于销售、员工餐或探索便当其中之一**。便当不能在探索中兑换金币，采集奖励只在正常 `settleField` 时入仓。

这四类 Buff 暂时不引入全新的敌人、战斗状态、技能升级或独立便当背包。后续仍可用食材基础口味（辣／菌香／温和）丰富区别，但先不要叠加第二套 Buff 树。

## 6. 菜谱覆盖与内容收敛

v0.6.2 能对所有 168 种组合生成名字，但只有部分人工定义。本阶段不等于要精写 168 套价格、工时及加成。

内容分层：
- **一级（16–18 道招牌菜）**：正式名称、描述、菜价、基础时间、菜系风味、顾客喜欢谁、可产生哪些风格、推荐一种特殊成功烹饪操作。包含现有 12 道，并优先新增「葱爆牛肉」「洋葱炖牛肉」「蒜香包菜」「牛肉土豆煲」等对照明显的例子。
- **二级（通用菜系模板）**：肉类爆炒、清蔬小炒、菌香煸炒、肉类焖煮、田园汤煲等 5–7 类。其余真实食材组合用模板推导价格、时间、口味和名称，仍可**成功研发并上架**；不得再显示「未知食谱」。
- **三级（失败）**：完全未熟、漏料、严重焦糊不能解锁、不能上菜单。失败来源于真实动作／熟度，不是因为没有人工写出此配方名字。

明确游戏身份的边界：两种锅相同食材可能是两道菜；同锅同食材，行为再不同也是同一道菜的不同工艺变体。

## 7. 正确整合到经营流水，而不是模拟数字

1. 研究成功：从主线 `s.inventory` 通过一次性事务扣除实验投入食材，产出 `CookVariant`；失败也扣料但不收录；附完整事件摘要。
2. 图鉴：同一道菜展示已发现的主工艺，一键设为默认工艺；只对经过玩家操作的合法版本建立图鉴收藏；限制重复结果淹没 UI。
3. 备餐：三道上架菜保留不变，每道菜有一个已解锁的工艺版本。预制食物也记录工艺，不能在中途更换菜单时变身。
4. 点单：顾客真正看完菜单时锁定 `recipeId + variantId + tasteFit + price`；后续换菜或研究不会追溯修改旧订单。
5. 厨房：按该工艺实际时间调度，仍双厨位自动制作。真正开工才按实验配方原料签名扣料；严守余额、库存、幂等账本。
6. 销售与评价：菜落桌一次性记锁定售价；品尝后按 **实际口味匹配 + 该工艺品质 + 等待时间** 评价。不能在 `throw` 状态提前记账。
7. 员工餐：投喂当日指定工艺，一餐扣原料，使用独立喂食事务，基础菜系加成与工艺微加成按统一总上限结算。
8. 探索便当：进入探索前选已解锁工艺、准备一份并扣料；Field 只持有当次 buff 快照和一次性消耗标记；正常 `settleField` 才把搜刮食材入仓。
9. 日报：按 **菜名 + 工艺** 展示真实销量、平均评分、平均工位时间、变体售价差、员工餐节省时间/耐心、便当实际生效次数。避免把“理论增益”写成“已经救回三单”。

## 8. 拆分交付，确保每一版都能单独试玩

- **v0.6.3-A 统一字典 + 图鉴**：限定词条类型；精选菜名与模板；主线兼容旧菜谱和老存档；用真实研发保存多个版本。经营此时可以继续使用旧默认值，不冒险改经济逻辑。
- **v0.6.3-B 经营联动**：三个菜单的变体选择、客群适配、营业价格/时间及订单快照；完成实际流水与日报回归。
- **v0.6.3-C 员工餐联动**：将已保存版本用于阿火/小芽投喂，继承每天一次和上限、成本结算。
- **v0.6.4 探索便当**：在探索之前引入选择/扣料/一次性效果；验证安全线可不带便当、不被强迫生产某道菜。

每个子阶段都要有手机 H5 390×844、375×667、320×568 的不滚动检查；至少一条真实链路：采集→研发→选择工艺→菜单→顾客点单→制作→上菜→评价→日报。探索便当再追加一条：前日研发→次日携带→一次性生效→探索结算。

## 9. 首轮可玩性检验（验收阈值建议）

- 相同食材与厨具，玩家能做出至少 **3 种有不同经营取向** 的成功变体，且平均 3 次试验不全是同一词条。
- 初级食材在不执行花哨手法时仍有较高可售概率；明显过早起锅要真实失败，但不鼓励死记秒数。
- 同一组订单需求、同一 seed，下厨房工艺 A/B 经营至少展示一个真实可解释差异：少等一秒、额外评价匹配、或每份加价 2 金币（均有取舍）。
- 三道菜和双工位不因工艺选择出现无法开业的死锁；可用兼容的基础工艺兜底。
- 旧存档中的所有已学习菜谱与品质保持不丢；失败不收录；探索便当与员工餐不能双花同一份原料。
- 至少 1 位用户真实在 iPhone 上连续玩 10 次研发 + 一晚经营，判断是否仍想换时序/手法或换一家顾客方向，而不只是为了刷数值。

## 10. 明确不做

暂不加第三厨具、更多操作、回合制、精确 QTE、战斗新职业、复杂库存料理成品背包、随时调菜单三种手工工艺切换、168 份独立平衡、无限可叠加词条及消耗后永久驻留的便当 Buff。

**本文件属于建议，尚未改变任何游戏引擎、库存、经营时间或探索状态。批准后再按阶段提交独立 PR、跑真实回归。**
