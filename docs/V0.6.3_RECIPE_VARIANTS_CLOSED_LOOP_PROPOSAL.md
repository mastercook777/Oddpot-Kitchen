# 《怪味食堂》v0.6.3 · 料理工艺收敛与跨系统收益设计（讨论草案）

**状态：待确认的设计草案，尚未开发，不代表已经实装或平衡通过。已根据玩家反馈（2026-10-11）重大修订：取消「通用词条＝固定 Buff」，改为「菜谱 × 工艺适配 × 完成质量」。**  
基线：GitHub `main` v0.5E.1 经营引擎 + 已验证有反复研发动力的独立 `experiments/v06-2-two-pots-cooking.html`。  
日期：2026-10-11。

## 0. 目标：不是更多烹饪动作，而是料理研发→应用→反馈→再研发

玩家已经认可「选厨具和食材 → 自由实时下锅 → 翻炒／颠勺或轻搅／收汁 → 根据投放顺序、动作和时间得到工艺词条」的基本体验。收敛意味着：

1. 不扩充基础厨具、操作种类、三段格子与 QTE。
2. **同食材、同厨具固定菜谱身份；操作改变工艺，不改变菜谱 ID。** 换厨具才可以改变菜名与生产工位，如牛肉+洋葱：炒锅「葱爆牛肉」，深锅「洋葱炖牛肉」。
3. 不企图手工数值策划 168 道菜。8 食材中任选 2–3，共 84 组合 × 2 锅具 = 168 组合身份；保留生成命名兜底，优先精制已有的 12 道及新增 4–6 道招牌菜与若干菜系模板。
4. 从实验中提取一条工艺风格、最多一条辅助风味、一个完成品质；动作标签仅描述做法，并不自带 Universal 加速、加价、增伤或员工效果。完整事件日志用于解释／图鉴，不无限叠加增益。
5. 失败（夹生、漏料、严重焦糊）真实消耗试验原料、不可收录上架；稍欠火低品质可以收录。避免过高失败率。
6. 各系统收益取决于**菜谱身份 × 该菜的工艺适配 × 实际质量**，不要求每种词条在上架、员工餐、探索中都产生增益。实体料理在三种用途之间只能选一种，真实耗料。

## 2. 统一数据模型

- `BaseRecipe`：`recipeId, ingredientSignature, vesselType, name, baseTime, basePrice, baseTasteTags, materialCost, curatedTier, techniqueProfile`，其中 techniqueProfile 是该菜对工艺的适配和专项收益配置。原 `RECIPES` 可经兼容解析器读取；不要在运行时动态修改原始常量。
- `CookVariant`：`variantId, recipeId, ingredientIds, vesselType, style, secondaryTrait, quality, valid, techniqueSummary, discoveredAt`。style 是真实烹饪行为的标签，不直接携带通用经济 Buff；需经菜谱专属的 techniqueProfile 解析。优先保留每菜谱×主风格的代表记录及少量特色版本。
- `activeMenuVariant`：`recipeId => variantId`。主菜单仍三道菜，同日换工艺可在准备阶段完成。已经点单的客人和已经预制的实物必须保存旧工艺快照。
- `CookEvent`：下料 `{ingredientId,t}`、动作 `{type,t,ingredientsAlreadyInPan}`、起锅 `{t}`，提供可解释的后端判定，界面不需要显示公式。

注意当前 `chili_meat` 允许 `beef+chili` 替代 `chicken+chili`，但旧菜谱原料表仍是 `chicken+chili`。集成时必须把**实际实验使用的食材签名**放进版本/配方实体，否则研发用牛肉、营业却扣鸡肉。旧存档兼容策略要写专项测试。

旧 `s.recipes[recipeId]=质量` 映射为 `legacy-standard` 默认工艺，保留原售价、工时、解锁、员工餐与菜谱三格。新字段以可选字段迁移，不要求强制清空已有存档。

## 3. 菜谱 × 工艺适配：新核心规则（取代 Universal Buff）

### 3.1 工艺只描述行为，不自带通用商业效果

- **烹饪事实层**：厨具、各食材下锅顺序与间隔、翻炒/颠勺/轻搅/收汁时机、熟度与成品质量，识别「家常」「爆炒」「香味十足」「浓香收汁」等风格。
- **具体菜谱层**：一道菜追求什么口感/味型？例如辣椒炒肉天然适配爆炒；清炒双蔬更重视清爽熟度；蘑菇焖鸡偏温润；森林浓汤偏醇厚。
- **适配解析层**：该菜与该工艺结合，才计算独有的风味变化、顾客偏好、是否有额外工序/售价价值，以及某些员工餐或探索便当的专属效果。
- **完成质量层**：好食谱也能做坏；不契合的做法也可熟制可售。失败仍由夹生、严重焦糊或漏料决定，而非与招牌做法不符直接判失败。

**不能再写「爆炒必定出餐 -1s」「家常固定品质 +2」「浓香收汁必定加价」「香味十足固定偏好 +8」**。这些旧设想已废止。不同菜谱、同一词条的效果可以不同，甚至为零。

### 3.2 首轮重点菜的工艺适配样例（方向，不是已确认平衡）

| 菜谱和厨具 | 强适配做法 | 其他成立的路线 | 本菜独有的风味因果 |
|---|---|---|---|
| 辣椒炒肉 / 炒锅 | **爆炒** | 家常、香味十足 | 辣椒和肉经颠勺形成锅气与辛香；对喜欢辛辣的客人更有吸引力。家常可以更温和，并非强制低品质 |
| 焦香蒜牛 / 炒锅 | **香味十足、爆炒**（两条候选） | 家常 | 蒜瓣提前入锅突出香味，肉类与蒜香同锅颠勺体现焦香，值得保留两种有不同偏好的版本 |
| 清炒双蔬 / 炒锅 | **家常、爽脆** | 翻炒均匀 | 追求清爽口感，过度高温可能影响品质，不能自动因为爆炒加速就成为最优 |
| 蘑菇焖鸡 / 深锅 | **清润慢炖** | 浓香收汁 | 轻搅、充分炖煮带来温润菌香，收汁走浓郁路线但不一定更贵 |
| 森林浓汤 / 深锅 | **浓香收汁** | 清润慢炖 | 菌菇与土豆形成浓稠汤感；收汁在这道菜上是招牌，不代表全部深锅菜都要收汁 |
| 葱爆牛肉 / 炒锅 | **爆炒** | 香味十足、家常 | 洋葱先煸再颠勺突出锅气；其他投料顺序可保留牛肉本味 |
| 洋葱炖牛肉 / 深锅 | **浓香收汁、清润慢炖** | 家常炖煮 | 味道醇厚和温润各适合不同经营情境，不能简化成一条绝对最优路线 |

用户举出的「家常豆腐」很适合作为**未来**例子：家常做法最可能突出软嫩入味，而过度猛烈爆炒未必适配。**当前原型只有 8 种食材，还没有豆腐，不得冒充现有正式菜谱。**

工艺适配至少有四个档位：**招牌 / 适合 / 普通 / 不契合**。这是菜品口味的契合度，而不是品质分数或自动失败开关。一个优秀的普通做法，可以击败做坏了的招牌工艺。

### 3.3 对玩家可见的结果

比如同一批野牛肉与火椒做「辣椒炒肉」：
- 玩家快速下肉，火椒随后加入，再熟练颠勺，得到「爆炒」「锅气」；这条在辣椒炒肉上可能派生菜品专属的「辛香锅气」，提高偏爱辛辣锅气客人的风味匹配。
- 玩家采用平稳翻炒，自然熟制，得到「家常」；这条仍可上菜单，实际品质很高时仍有吸引力；也许对家庭客更易入口。
- 并不是爆炒自动缩短所有菜品生产时间；如果确实想给辣椒炒肉的一种高效工艺节省 1 秒，也应在**该菜×该工艺的配置**里决定，不从爆炒词条统一发放。

**菜名是食材和锅具的身份，基础工艺是操作事实，派生风味描述来自菜谱与操作的匹配。** 例如「辣椒炒肉 · 辛香锅气版」而不是任何菜只要颠勺都变成一样的经营属性。

### 3.4 配置复杂度与收益上限

- 精写 12 道当前正式菜谱，再选择 4–6 道实验中的招牌候选；每道最多重点设计 2–3 条工艺适配和个别配对效果。
- 其余 168 个锅具×食材组合使用 **5–7 种菜系模板** 默认解释：肉类快炒、菌菇小炒、田园素炒、肉类焖炖、汤煲等；允许招牌菜覆盖模板。
- 将可解释的经营修正独立建模为：风味修正、工序时间修正、可选的价格修正。**没有合理因果就保持零修正**，不为了让每个词条“看起来有用”而硬塞效果。
- 客群的额外匹配建议单个工艺最多 +8 且只计算一次，不要再把派生词条作为新的固定标签重复吃旧引擎的每标签 +20。
- 原基础工时和售价仍由菜谱定义，员工/锅位升级/事件收益继续按已有规则叠加并封顶，不能强行改写进行中的订单。
- 研发达到高适配依然需要操作到位；严重夹生/焦糊仍是失败。

建议数据结构（示意）：每道菜的 techniqueProfile 包含对工艺键的 affinity 档位，并可选 pairEffects；派生结果由统一解析函数生成有效风味标签/客群适配/必要的生产工序调整。**同一个风格键在两个菜谱里不能被默认解释成同一组经济收益。**

## 4. 员工餐：先看菜谱，再看该菜与工艺的结合

当前主线：帮厨阿火基础省 1s，辣味炒锅岗位另省 2s、菌香 +1s、优秀品质（至少 85）另省 1s，合计最多省 4s；跑堂小芽基础耐心 +3s，温和菜 +6s、菌香 +4s、其他 +2s，优秀品质另 +2s，合计上限 +12s。真实扣料、每天每员工一次、熟练微成长等原规则不变。

**不要将「阿火吃任何爆炒版必省 1 秒」「小芽吃任何家常版必多 1 秒」写为 Universal Buff。**

新的员工餐算法遵循：
1. **先菜谱本身味型**：是否辣、菌香、温和、饱腹等，继承并解释旧算法。
2. **再查具体菜谱×工艺的员工餐适配**：如阿火吃爆炒辣椒炒肉可能特别契合炒锅岗位，阿火吃爆炒清炒双蔬不应有同样收益；小芽吃清润慢炖蘑菇焖鸡可能特别适合家庭客安抚。
3. **最后按岗位、品质和旧上限结算**。每道菜不一定有特别的员工餐效果；没有就保持原基础收益。
4. 员工餐选择 UI 应预览实际的「省秒数 / 耐心」以及封顶后的增量，避免告诉玩家获得了实际上被上限吞掉的 Buff。

以此确保员工餐选择是选什么菜、用什么做法，而不是找一个跨菜复用的万能词条。

## 5. 探索便当：菜谱决定能力，做法决定适配和强度

当前游戏阶段顺序为 **forecast → field → research → menu → prep → service**，所以带便当必须在次日探索前选择昨天或更早掌握的工艺并真实扣料。一天最多带一份，安全路线允许不带便当。

**取消旧草案的统一映射：爆炒≠必定移动加速、香味十足≠必定额外采集、家常≠必定减伤、浓香收汁≠必定回血。** 这些应与具体菜谱挂钩。

| 具体菜谱 | 候选基础便当功能 | 该菜的工艺如何影响 |
|---|---|---|
| 辣椒炒肉 | 辛辣御寒/抵御一次相关环境伤害 | 爆炒产生的辛香锅气可强化**辣椒炒肉**的专属效果；家常版依然能保留温和基础收益 |
| 蘑菇焖鸡 | 暖胃续航/第一次受伤时减轻损失 | 清润慢炖若对本菜契合，可强化可靠性；不是所有清润慢炖都自动减伤 |
| 森林浓汤 | 菌香寻踪/首次合格采集有机会获得额外材料 | 浓香收汁强化**森林浓汤**的采集特长；不扩散成通用「收汁必加采集」 |
| 葱爆牛肉 | 饱腹提神/小幅移动效率收益 | 爆炒是这道菜的招牌做法时，才能发挥额外效果；家常不必等额 |

以上都是**待验收的提案效果**，还没有实装，且需匹配现有森林/热泉危险与背包容量。不要做脱离现有探索系统的额外生命、材料或速度魔法；若选择伤害、额外采集等一次性事件，必须与现有探索伤害/背包及结算共用一条权威路径。

工艺已学会不等于免费获得便当。仍通过引擎独立幂等事务扣掉该份菜真实所用材料，并在探索开始时锁定一次性效果快照，只有已有 settleField 负责将背包物资结算入库。

## 6. 菜谱覆盖与内容收敛

v0.6.2 能对所有 168 种组合生成名字，但只有部分人工定义。本阶段不等于要精写 168 套价格、工时及加成。

内容分层：
- **一级（16–18 道招牌菜）**：正式名称、描述、菜价、基础时间、菜系风味、顾客喜欢谁、**对不同工艺的适配档位及专属效果**、推荐观察的烹饪动作。包含现有 12 道，并优先新增「葱爆牛肉」「洋葱炖牛肉」「蒜香包菜」「牛肉土豆煲」等对照明显的例子。
- **二级（菜系适配模板）**：肉类爆炒、清蔬小炒、菌香煸炒、肉类焖煮、田园汤煲等 5–7 类，负责没有手工覆盖的菜谱对工艺的默认适配。其余真实食材组合用模板推导价格、时间、口味和名称，仍可**成功研发并上架**；不得再显示「未知食谱」。
- **三级（失败）**：完全未熟、漏料、严重焦糊不能解锁、不能上菜单。失败来源于真实动作／熟度，不是因为没有人工写出此配方名字。

明确游戏身份的边界：两种锅相同食材可能是两道菜；同锅同食材，行为再不同也是同一道菜的不同工艺变体。

## 7. 正确整合到经营流水，而不是模拟数字

1. 研究成功：从主线 `s.inventory` 通过一次性事务扣除实验投入食材，产出 `CookVariant`；失败也扣料但不收录；附完整事件摘要。
2. 图鉴：同一道菜展示已发现的主工艺，一键设为默认工艺；只对经过玩家操作的合法版本建立图鉴收藏；限制重复结果淹没 UI。
3. 备餐：三道上架菜保留不变，每道菜有一个已解锁的工艺版本。预制食物也记录工艺，不能在中途更换菜单时变身。
4. 点单：顾客真正看完菜单时锁定 `recipeId + variantId + tasteFit + price`；后续换菜或研究不会追溯修改旧订单。
5. 厨房：按该工艺实际时间调度，仍双厨位自动制作。真正开工才按实验配方原料签名扣料；严守余额、库存、幂等账本。
6. 销售与评价：菜落桌一次性记锁定售价；品尝后按 **实际口味匹配 + 该工艺品质 + 等待时间** 评价。不能在 `throw` 状态提前记账。
7. 员工餐：投喂当日指定工艺，一餐扣原料，按菜谱基础味型及本菜×工艺专属适配算增益，继承原技能上限。
8. 探索便当：进入探索前选已解锁菜谱与工艺、准备一份并扣料；菜谱决定便当能力，合适工艺决定强化；Field 仅保存效果快照/一次触发标记，照旧通过 settleField 入仓。
9. 日报：按 **菜名 + 工艺** 展示真实销量、平均评分、平均工位时间、变体售价差、员工餐节省时间/耐心、便当实际生效次数。避免把“理论增益”写成“已经救回三单”。

## 8. 拆分交付，确保每一版都能单独试玩

- **v0.6.3-A 统一字典 + 图鉴**：限定工艺词条；优先为 12 道现有菜 + 4–6 道精选菜制作**菜谱×工艺适配表**，再做菜系模板；兼容存档，真实研发保存多个版本。经营此时可以继续使用旧默认值，不冒险改经济逻辑。
- **v0.6.3-B 经营联动**：按菜谱×工艺配对结果确定客群偏好及个别菜的工时/价格变化，订单快照与日报回归。检查同一种词条在不同菜谱上不会得到统一收益。

## 9. 首轮可玩性检验（验收阈值建议）

- 同一菜谱能由不同下料时序与动作做出 2–3 种有差异的成功工艺，但**不强制所有菜拥有三种同等价值的路线**；强适配不自动保证高品质。
- 初级食材在不执行花哨手法时仍有较高可售概率；明显过早起锅要真实失败，但不鼓励死记秒数。
- 同一组订单需求和同一 seed，某道菜的工艺 A/B 需展示可解释的评价、风味或工序差异；不同菜的同名工艺不强制相同经济效果。
- 三道菜和双工位不因工艺选择出现无法开业的死锁；可用兼容的基础工艺兜底。
- 旧存档中的所有已学习菜谱与品质保持不丢；失败不收录；探索便当与员工餐不能双花同一份原料。
- 至少 1 位用户真实在 iPhone 上连续玩 10 次研发 + 一晚经营，判断是否仍想换时序/手法或换一家顾客方向，而不只是为了刷数值。
