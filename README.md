# 怪味食堂 · 移动 H5 核心玩法验证 v0.2

基于《怪味食堂》GDD v0.2（最高规则优先级）、Codex MVP 开发交接包，以及 GDD01–04 非冲突的详细规则制作。

## 玩法

- DAY 1–3：营业情报 → 路线采集/跳过 → 研发 → 三菜 Build → 备餐 → 3 波营业 → 日报 → 永久升级；第三天挑战替换正常营业。
- 3×3 炒锅：6 食材、爆炒与焖煮、3 离散拍、每拍最多一次换位、食材热量、邻接联动、4 基础菜 + 1 隐藏变体。
- 菜单：三槽、WOK/POT 双工位、辛香暖胃/菌香组合、有限库存、固定 7 个模拟订单、口味/耐心/品质/服务满意度。
- 最后一天爆炎厨王采用统一订单结果四轴评分，永久奖励猛火掌控。
- 本地 localStorage 存档，固定 seed、唯一事务 ID；适合 Safari 触控、点击两格交换或拖动。

## 部署到 GitHub Pages

直接把本仓库内容上传到 **新的** GitHub 仓库（不要复用别的游戏仓库），然后在 Settings → Pages → Build and deployment → Deploy from a branch → `main` / `/ (root)` → Save，即可打开 `https://<username>.github.io/<repo>/`。根目录 `index.html` 使用相对 `./src/` 路径，无需构建步骤。

## 体验验证重点

1. 第一天做菌香与焖鸡，第二天采火椒研发辣椒炒肉，菜单更换有没有明显价值？
2. 炒锅的加热与一次换位，像做饭还是像数学题？
3. 同类 WOK 菜集中与 WOK+POT 混搭是否确实改变拥堵？
4. 重要订单手动烹饪品质收益是否值得时间与材料风险？
5. 第三天能否看出为什么赢/输，并愿意调整下一轮菜单？

## 已知取舍

- 探索为**可点击的节点决策原型**（安全/高风险、采集/回店、材料实际入库），不是有摇杆移动和自动战斗的 2D 实景。
- 固定顾客顺序示范策略因果，后续应按 seed 生成主题变体、随机事件。
- 工位推进采用浏览器模拟秒钟，不依赖手机后台真实时间；挂起后恢复原进度。
- 目前没有完整厨房动画、正式美术、音效、充值、联网或广告。
- 仍需 iPhone Safari 真机测试、手动订单完整性检验、数值及软锁压力测试。


## v0.2 经营场景与触控交互（2026-10-09）

本次主要验证开罗游戏启发的**俯视角小餐厅经营**，不追求正式像素美术，也不照搬具体视觉素材：

- 餐厅场景可见墙壁、门、两张桌子、顾客像素占位角色、桌上的点菜气泡和实时等待条；WOK/POT 双工位可见制作状态。
- 顾客到达时获得真实桌位；订单完成或离店会腾出桌子，再按固定序列接纳后续顾客。
- 点击餐桌定位订单，执行「插队优先」或「主厨亲做」；点击锅具查看工位当前任务与排队。两个锅具可并行，单锅任务严格串行。
- 明确的开门/暂停/恢复按钮（修复 v0.1 营业默认暂停但页面没有继续按钮的问题）；切后台自动暂停。
- 两次波间休整可择一紧急预备餐（真实耗材、真实成本），或直接迎下一波；数据仍进入统一营业日报。
- 炒锅加入**试验性**三档火力、颠锅和下一拍受热预测；这些是为了降低纯数字拼图感的探索性原型，并非已通过玩法验收的正式规则。

**目前仍未完成：**真正自由行走的顾客/店员 AI、家具摆放和装修、像素角色行走帧、独立美术素材、带速度的实时锅气/音效与 iPhone 真机触控回归。不要将本版误称为完整的开罗式经营模拟。

**玩法验证问题：**点击桌子调整订单是否比列表操作更自然？第 2 波高峰是否形成可理解的锅具选择？经营结果是否能反推菜单调整？

本地运行：`npm install && npm run dev`，运行自动测试：`npm test`。GitHub Pages 使用仓库根目录的 `index.html`，`standalone.html` 仍为旧版离线备份而非 v0.2 入口。
